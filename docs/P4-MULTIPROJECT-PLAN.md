# P4：统一多项目管理实施方案

2026-11-03 范围补充：用户授权本机 osa 随 Orca 启停及异常恢复，采用独立 LaunchAgent 和原服务启动器，原信箱看门狗不变。下文“不做新的进程看门狗”是此前阶段边界，由此次授权补充；跨机器常驻/接管仍留在 P5。配置与暂停方式见 [运行手册](p4/RUNBOOK.md)。

状态：2026-11-02，用户已授权先实现 1–4，多机常驻/自动接管作为 P5。P4 第一版已实现，真实双项目并行、联合验收、Router 唤醒及飞书查询回传通过，审查修复后 293 项测试与类型检查通过，证据见 [P4 验证记录](p4/VERIFICATION.md)。以下保留设计依据和边界；第一版远程操作仍通过本机 Orca 窗口中的 SSH，不建设跨机器派工系统。

补充约束：项目管理必须通用，不绑定当前机器或示例项目；优先级不表示只执行最高优先级。项目知识、任务状态和模型会话分别管理。多机器自动接管是下一阶段目标，本轮不实现。

## 目标和边界

用户可以交替在指定飞书群与指定 Orca Router 窗口提需求、补充同一任务、查询各项目进度和调整优先级。一个管理服务接收消息、保存任务、汇总状态；Executor 按任务启动，独立 Claude 审查继续保留。不要为每个项目部署独立服务或维持一个永久模型会话。

继续复用 vendor/dsh-core 的准入、工单、订阅、派工与回复机制，不修改 vendor。Orca 负责真实项目、工作区、终端、Run、Task、Dispatch 和生命周期。新增业务项目归属、任务关系及明确执行目标；不做 Web 面板、自动模型选择或新的进程看门狗。

## 项目组织

业务项目与代码仓库不是一一对应。提供通用登记、修改、归组、查询和归档能力，项目名称、组件数量、机器和路径全部是数据，不能写进业务代码。Orca 是现有执行适配器和发现来源，不是业务项目目录的定义。任意新项目可以登记；登记与当前执行器能否执行分开表达，未连通或尚不支持的目标明确显示状态。

下表只是根据用户当前项目形成的首批示例和验收样本，不是内置项目白名单：

| 业务项目 | 组件及 Orca 仓库 |
|---|---|
| SoulShift | SoulShift |
| Super-agent-orca | Super-agent-orca |
| 智能客服 | smart-cs-panel、game-ai-cs-report、smart-cs-agent-hermes（客服 Hermes 核心） |

分支和 worktree 属于组件下的具体工作环境，不各建一个业务项目。已有 smart-cs-agent、smart-cs-agent-v2、上游 hermes-agent 等条目先作为待核对关联，不凭目录名断定是现役、废弃或生产版本。

从 Orca project/repo/worktree API 获取稳定标识、机器、目录、分支和原生状态；只额外保存业务分组、别名、用途及用户确认的默认执行位置。Orca 列表是发现来源，不意味着所有发现的仓库自动获得执行授权。清单不可达或过期时保留最后观察时间，不静默改指向。

业务项目用稳定 ID，重命名不改变身份；组件关联仓库身份，机器上的具体副本是执行位置。同一项目可以有多个执行位置，同名路径在不同机器上不是同一工作区。SSH 别名只是某台执行机的连接配置，不作为跨机器全局身份。同步清单不删除业务记录或覆盖用户确认的用途。

每个执行工单在派工前固定业务项目、组件、Orca 标识、工作区选择和分支基线。项目默认值以后改变不移动运行中的任务；遇到多个候选工作区，用选择题问用户，不猜“最新”目录。沿用隔离 worktree 的既定执行方式，已有工作区被人或其他 Agent 占用时不直接接管。

## 两个入口如何接续

- 同一服务统一读取一次飞书来源，避免每个项目重复监听同一群。GitHub 来源按已登记仓库归属组件。
- 同一话题内的后续消息沿用已关联任务；跨入口明确指出任务编号或唯一任务时，记录关联后进入同一工单。没有足够信息时呈现候选，不靠全局“最近一个任务”猜测。
- 普通提问只返回信息，不自动创建开发任务。Router 可以读取项目摘要、任务和证据索引；代码调查、技术拆分及实施方案仍交 Executor。
- 消息、任务和派工使用稳定身份；跨入口关联不能复制工单或重复执行。既有本人准入、租约、已读确认和发件箱去重规则继续执行。
- 当前提问在当前入口回答；任务结果回任务已登记的反馈话题。增加反馈入口要明确登记，不默认把全部日志广播到两个入口。

## 管理能力

第一版提供项目清单、组件和工作区列表、任务状态、阻塞项、待决策事项、优先级、项目暂停后续派工及任务关联。每条进度显示证据来源和更新时间；区分 Agent 报告、检查通过、独立审查通过、已合并和已部署，不将它们互相等同。

优先级影响资源竞争时的选取顺序，不是只开放最高优先级队列。有空闲资源、无冲突且依赖满足的任务可以同时运行。以项目轮转、项目内优先级和等待时间排序实现有限公平调度；持续新来的高优先级工作不能令其他项目永远得不到执行机会。调整优先级不抢占正在运行的任务。

暂停项目先阻止新任务启动，正在执行的任务保留并说明状态。停止正在运行的任务沿用明确停止流程，不用优先级调整偷偷中止工作。

跨仓库需求保存一个业务目标及其子工单关系；每个子工单仍有自己的执行目标和验收证据。技术拆分由 Executor 提出，程序校验子任务不扩大授权范围。已有两层 Executor→worker/独立 reviewer 结构不再增加一层原生 worker 嵌套；总目标是程序记录，不是必须常驻的额外 Agent。

依赖以明确记录为准，检查自依赖和环；只有前置任务达到指定验收条件才派发后续任务。全部子任务 ready 不自动等于联合验收通过；联合验收作为有范围和检查结果的独立任务。提交、推送和发布继续遵循用户授权，按集成版本交付。

P4 交付包含可配置的有限并发，初始建议两个 Executor 工单并行，独立审查和子 worker 的额外消耗须在状态中可见并受相应启动约束；不以现有单槽实现作为多项目阶段最终能力。同一可写工作区不能有重叠编辑。独立 worktree 也可能共用端口、测试数据库和远程部署目标，明确共享目标的任务应串行执行。资源不足限制并发时说明实际原因，而不是称为“只执行第一优先级”。

## 状态、知识和模型上下文

避免把整个系统依赖在一个长期聊天窗口的“记忆”上，沿用现有数据库和项目文档，不引入独立记忆框架或向量数据库。

| 信息 | 权威来源与范围 | 使用方式 |
|---|---|---|
| 业务项目、组件和任务归属 | 管理服务的稳定 ID 与关联记录 | 所有查询和操作必须带明确范围 |
| Run、Dispatch、工作区与存活事实 | Orca 原生记录及执行主机的观察 | 附来源和观察时间，不用摘要推翻原始证据 |
| 工单授权、依赖、派工、报告和验收 | 管理服务的持久记录 | 程序校验状态变化，旧 attempt 不得覆盖当前执行结论 |
| 项目规则和已经拍板的决定 | 对应项目文档或显式确认的决定记录 | 保存来源与适用范围，新决定标记取代旧决定，不悄悄覆盖历史 |
| 项目进度摘要 | 从以上记录生成的派生内容 | 可以重建，带更新时间；不能作为唯一完成证据 |
| Executor 的临时推理与聊天历史 | 对应任务/attempt 的会话 | 按需加载，不自动升级为其他项目的长期规则 |

跨项目共享知识必须明确标记适用范围；一个项目里的推断不能自动变成全局规则。Router 默认只读目录、相关摘要和当前任务，需要时检索证据；Executor 按当前授权加载项目规则、任务输入和工作区信息。输入顺序由服务持久记录，不靠聊天窗口顺序猜测。

检查包括同名任务跨项目不串联、项目重命名不丢关联、旧报告不能覆盖新 attempt、跨入口补充不重复派工、重启后状态一致、过期摘要不被当成当前进度。测试验证约束，不能用设计文档承诺绝不会混乱。

## 远程机器：先用 SSH

第一版不实现 Orca `worker-start --on` 远程派工，不新增远程 Agent 守护进程或网络回报服务。Executor 和 reviewer 留在本机 Orca，必要时通过用户已有 SSH 配置访问远程机器，继续使用现有本地 osa 回报通道。

SSH 操作记录主机别名、远程目录、用途和检查证据，不保存私钥或口令。区分“本地开发、远程验证/部署”和“代码只在远程”；只按实际需要接入具体远程环境，不把同名目录视为同一项目。

本地代码修改仍用已有文件指纹与独立审查。若任务需要直接修改仅在远程的代码，在投入使用前必须补充针对该远程目录的独立检查和版本/内容证据；当前本地 ReviewGate 不能证明远程文件已被审查。尚未完成此项时明确标记未验收，不用本地 ready 伪装远程完成。SSH 失联表示结果待核对，不能证明远程进程退出，也不能盲目重放有副作用的命令。

只有 SSH 方式不能满足真实任务（例如本机离线仍要自治执行），再讨论原生远程派工。它不阻塞本地多项目管理交付。

## 实施顺序与验收

| 阶段 | 交付 | 可观察验收 |
|---|---|---|
| P4-A 项目目录与本地多项目执行 | Orca 清单同步、业务分组、任务目标绑定、按目标选择仓库、旧状态兼容 | 两个隔离测试仓库分别执行任务；文件、审查和发布目标不串仓；旧 P3 state 重启不重派 |
| P4-B 双入口与项目总览 | 跨入口明确关联、项目/组件状态查询、优先级、公平并发、暂停后续派工 | 飞书创建任务，Router 补充，同一任务收到且确认；反向接续同样通过；歧义不派工；两个不同优先级的独立项目能并行，高优先级持续到来时低优先级仍获进展 |
| P4-C 跨组件工作 | 业务目标、子工单、依赖、联合验收记录 | 隔离测试中的两个仓库协作完成一个目标；失败前置阻止依赖启动；修复后续接；联合验收结果可追溯 |
| P4-D 日常使用 | 一个可恢复的服务启动入口、指定 Router 窗口绑定、可靠唤醒与租约接管 | 不依赖本次实施对话人工轮询；服务/Router 重启后未处理消息保留，无重复派工；Router 不在线时明确显示待判断 |

Router 唤醒优先验证 Orca 已有机制，只有确认投递且旧 Router 身份已失效才接管；不反复向正在输入或用户接管的终端注入提示。不修改现有邮箱看门狗承担新的生命周期职责。第一版随本机 Orca 使用，不承诺 MacBook 休眠或离线期间持续执行。

这里的离线需要分开描述：关机/休眠会影响本机执行；只有网络断开时本地任务可能继续，但飞书和 SSH 不可用；主服务或 Router 停止也可能令新请求无法处理，即使电脑仍开着。另一台服务器仍开机不表示它会自动接管。远程命令是否继续取决于其实际进程托管方式，不能从 SSH 断开直接判断。

“一套系统”指一个权威管理服务，不要求永远部署在这台 MacBook。若需要笔记本关机后继续接单，可将管理服务和具备所需运行条件的 Router/Executor 放在常开机器，其他设备作为入口或执行目标；迁移前要验证 Orca/Agent、账号和本地项目可达性，不能只移动 SQLite 文件就宣称可用。

“任意一台活着就能自动接管”属于另外的高可用要求，涉及一致状态、单一派工权及旧实例隔离，当前不默认实现。禁止多台机器各启动一套独立协调者同时监听同一群，也不把 WAL 数据库放在网络共享目录让多机同时打开。未来选用常开单主机还是主备接管，由用户明确持续运行需求后再决定。

SSH 验收按第一项实际远程任务单独增加，先读取主机和目录证据，再在授权测试位置验证；不因编写本方案而连接或修改任何生产服务器。

## 代码改动范围与兼容性

- 复用 Store 保存项目和工单目标等附加记录，先保持一个 Engine 和数据库；无需为多项目复制整个核心或引入微服务。
- App 的接单和关联增加目标校验；OrcaExecutor 从工单固定目标获取仓库/工作区，替换目前全局唯一 repository 假设。
- ReviewGate、Publisher、GitHub 来源与 CLI 配置都必须使用同一目标绑定，不能只修改派工路径。发布账号和远端匹配仍逐工单校验。
- 新记录由统一服务写入；对旧单仓库 state 映射为一个兼容项目，先备份、保留原 ID、来源游标、能力令牌和外部回执，不重新导入历史消息或重建原 Task。
- 非 Git 目录的执行/审查不能直接套用现有 Git 指纹；当前已登记业务仓库优先，普通文件夹支持遇到实际需求时单独验收。

每阶段运行与改动对应的检查；真实业务项目先只读发现，改动隔离测试仓库完成验收后才交付。文档中的拟议管理能力不能在测试通过前记为已实现。

通用性验收必须临时登记与当前三个项目无关的新项目，完成归组、执行、重命名和归档；不改源码即可工作。初始在本地验证不意味着数据模型只能表示本机，远程执行能力按 SSH 小节单独验证。
