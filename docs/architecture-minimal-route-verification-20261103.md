# 最小路线需求验证

2026-11-03。结论：**只保留“Orca retry + mailbox、OSA 接受回执、Orca 输入留存/来源”的简写路线，不能覆盖全部需求。v2.1 中的前驱保护、责任消费和独立投递不能被一起删掉。** 完整路线仍可沿现有 DSH/Orca 实现，但尚未证明全部需求通过；本轮没有交付生产修复。

验证对象是当前源码加上一轮隔离实验中的最小报告 receipt 原型，不是一个已经实现全部 v2.1 条款的版本。输入可靠保留和原生身份接入尚未实现，不能把它们当成本轮通过的前提。前轮原生证据见 `architecture-native-experiments-20261103.md`。

## 本轮实验

复制当前源码、vendor 和测试到临时目录；业务数据库均新建。没有修改生产源码、业务库、配置、服务或 Orca 源码。归档时逐文件核验 src/vendor/bin/scripts 与当前工作树字节相同。

新增 App 实验复用真实 App/Store/DSH，executor 使用夹具；报告接受使用上一轮相同的 `Store.atomic(App.handle + reportId/payloadHash/receipt)` 原型。随后用真实 OrcaExecutor 和现有 fake Orca CLI 扩大接续反例的覆盖范围。

| 场景 | 结果 | 可得结论 |
| --- | --- | --- |
| A 等用户登录，B 完成，C 有进度，重开数据库 | 通过 | B 的结果 outbox、C 的通知独立可取；A 不必结束。尚不代表真实聊天已分别显示。 |
| 同一 ready 报告在重开后重放；同 ID 不同内容 | 通过 | 最小领域 receipt 能避免重复结果，拒绝 ID 冲突。认证是受控夹具。 |
| 已登记范围变更后，用旧 read 完成；只 ack 新输入后完成 | 通过 | 现有校验会拒绝；重新 read、ack 并报告处理输入后才完成。这里只覆盖已经进入 OSA 的消息。 |
| progress 带下一步，Router ack，执行轮次结束，重开 | **需求断言失败** | 工单未结束、没有新派工，但对应接续通知消失；自由文本 next-step 不会成为可消费动作。 |
| 先接受序号 2 的进度，重开后收到不同 ID 的序号 1 | **需求断言失败** | 两个 receipt 都存在，但当前报告回退为旧进度。当前接口不执行该实验提供的 sequence；去重不是顺序保证。 |
| Router 离线期间连续接受两项进度，重开后读取待汇报项 | **较强投递断言失败** | 只剩最新进度通知，早先报告没有独立待投递项。receipt 有历史数据，但没有对应消费/投递路径。 |
| 真实 OSA 执行适配：进度→原生夹具确认退出→退役→ack 全部通知→重开→三次 tick | **需求断言失败** | 原生绑定已 finished，业务未完成，原生启动次数仍为 1，且没有该任务的待办通知。证明执行适配也未自动补回接续责任。 |

最后一项使用 fake Orca CLI，不能当作真实原生 worker canary。它验证的是 OSA 已有适配路径：不是只因 App 夹具没有 executor 才出现断点。保守停止而不盲目重试是正确的；错误在于需要后续决定的责任可以随通知确认而消失。

关于进度合并：原始需求不必解释为每句中间进度都逐条推送。本实验采用了较强的“不静默丢已接受待汇报项”断言。如果允许合并，必须持久记录哪些报告被哪个汇总覆盖，并保留独立任务的待投递责任；当前只有 latest report 投影，没有这个保证。不能仅凭这一项断言断言所有合并都不符合需求。

另选取现有 App/Router/Review/Orca 测试：**10 项通过、107 项未选中**，覆盖范围修订、状态区分、重复提醒、review 时新输入、两个仓库并发、资源阻塞隔离、慢启动不挡其他监督、retry 不等无关 assignment 等。新增检查合计 **3 项通过、4 项需求断言失败**，其中两项从不同层复现同一接续缺口。失败原样保留，未改成预期失败来制造全绿。

## 对原始需求的判断

| 需求 | 最小完整实现必须保留什么 | 当前证据与缺口 |
| --- | --- | --- |
| 补充消息/新要求不忽略 | Orca 可靠提交保留与可信来源；OSA 原子登记/游标；归属、范围版本及处理证据 | 已登记输入保护通过；原生 epoch 丢失反例仍未修复，可信来源和自动采集未完成。 |
| 持续推进，真实等待可解释 | 从 DSH 状态派生任务阶段；handoff/task-plan 只增加责任、等待对象、授权动作/版本、消费回执 | 本轮两层接续反例失败。通知 ack 不能关闭责任，只有具体路由决定/动作消费或领域结束能关闭。 |
| 无关任务独立推进/汇报 | 保留 assignment 独立执行；按真实依赖约束；既有 outbox 增加任务级进度待投递记录 | 并发与结果独立可取通过；Router 离线后的完整投递、慢 review/坏报告不挡其他任务尚未证明。 |
| 免手工重挂 | 现有 supervisor/pulse 和原生唤醒持续处理未消费责任；对账后重试沿同 Task | 有监督能力，但接续责任会丢；真实空闲 Router 被唤醒并完成决定仍需 canary。不能用 skill 要求手动循环充当恢复机制。 |
| 状态准确，旧 worker 不污染新执行 | 所有异步写入检查当前前驱/assignment/授权版本；复用原生尝试身份；报告顺序/拒绝结果持久化 | 原生 same-Task retry/熔断原语通过；当前旧 start 覆盖和普通 status 来源反例未闭合；本轮发现 receipt 不防旧进度回写。 |
| OSA 中断后的报告补交 | 原生 mailbox 接收成功→共用认证/review 入口→领域事务及 receipt→原生 ack；结果复用现有 outbox | 前轮三个真实进程崩溃点通过；真实 IPC、身份、review/撤销竞态、乱序和用户可见送达未验。 |

## 收敛后的最小完整路线

1. **输入入口**：优先扩展 Orca 既有 submission 写入点，满足独立于渲染 epoch 的保留、确认水位和可信来源；OSA 复用 Store 原子登记。gap 必须明确，不能自动跳到新 tail 后宣称无遗漏。
2. **执行边界**：修旧 start 及所有异步回写的前驱保护，接入可核验的原生 attempt 身份，保留同 Task retry、熔断和资源退出核查。普通 status 的自报 dispatchId 不作权限证明。
3. **报告接受**：复用 mailbox；OSA 只补领域 receipt 和每 assignment 的顺序/缺口/永久拒绝处理。在线与补交共用实际 socket 的认证及 review 校验，最终提交再次核对当前授权；每条任务独立推进，不能一个坏报告卡住整批无关报告。
4. **接续责任**：在现有 handoff/task-plan 保存不能派生的责任、等待条件、授权动作及消费证据。现有 pulse 扫描未消费责任；已有明确授权且条件满足才原子生成既有 job/派工决定，重放复用消费回执；缺业务决定时持续交给 Router。不能从自由文本 next-step 猜外部操作，也不能在 native stopped 后一律 retry。
5. **独立投递与状态**：用既有 DSH Replies/OSA outbox 保存每任务待汇报进度或明确的合并覆盖记录。业务阶段、原生存活、报告待接受、下一责任分别由各自事实派生。确认送达不等于任务完成或接续动作已消费。

这是 v2.1 已要求的闭环，不是新增第二套业务状态机。无需新调度器、九态持久状态、另一套完整聊天历史或默认第二报告队列；不修改 DSH vendor。DSH 继续管业务事实，Orca 管原生执行和运输，OSA 只补二者之间缺失的契约。与 DeepSeek 的代码关系沿用第二轮已核实结论，本轮未重新查上游 HEAD。

仅针对 OSA 不可用时补交，现有原生 mailbox 已有实验支撑；如果 Orca 同时不可用且仍要求客户端返回“已可靠排队”，必须另验客户端持久入口，不能把该故障窗口隐藏在成功承诺里。

## 验收与证据

不能给“全部满足”结论。进入集成验收至少要求：上述反例改后通过；T1–T12 未闭合项逐项补证；原生离线提交跨 epoch 全量恢复；真实新旧 worker 身份隔离；真实空闲 Router 自动接续；A 等人/B 完成/C 继续在真实投递链分别可见；组合重启、范围修订/撤销和慢 review 不造成旧状态复活。

本轮证据在 `.osa/architecture-fix-20261103/minimal-route-verification/`：README、完整隔离源码快照、源码哈希、测试源、执行命令及原始日志。无需依赖临时目录继续存在。本轮只增加此报告与隔离证据，未部署、未运行真实业务任务，也未重跑全部回归。
