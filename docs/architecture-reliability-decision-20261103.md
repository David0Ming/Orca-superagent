## 为什么适合采用

它把原来混在一起的确认分开，并明确每一阶段之后谁负责：

| 流程 | 可靠交接点 | 后续责任 |
| --- | --- | --- |
| 用户正常聊天提交 | Orca 可靠留存提交事件及来源 | OSA 登记、路由、处理；原生接收不等于要求已执行 |
| Orca worker 启动/重试 | 原生 Task/Dispatch 回执与 OSA 当前执行代匹配 | 当前执行及接续责任；旧回包不能重置绑定 |
| 报告进入 mailbox | 原生已认证持久接收 | OSA 可靠接管并按任务处理 |
| OSA 接管原生批次 | Store 保存全部项目和拒绝证据后 ack | OSA 的待处理记录；慢 review 不再占着整个原生批次 |
| 报告业务接受 | 领域变更与接受回执同事务 | 后续动作及任务级结果 outbox |
| 通知送达/被确认 | 只结束对应投递责任 | 未完成目标的接续责任继续保留 |

这直接对应已复现的输入遗漏、旧执行回写、报告缺失、通知确认后闲置和无关任务互等，而不是希望模型更认真记住上下文。

DSH 继续独占业务事实，Orca 继续提供原生重试、熔断、资源管理和 mailbox。OSA 只在现有 Store、handoff/task-plan、pulse、outbox 上补齐连接契约。与 DSH 的关系保持原来已核实的“复用固定提交的 core，外层适配由 OSA 实现”；本轮没有重新核对上游版本。

## 采纳的具体取舍

1. **必须涉及 Orca 改动。** 正常聊天的可信来源和跨 epoch 提交留存不能靠 OSA 读取渲染 history 补出来。保留稳定事件 ID、连续消费位置、未确认留存及显式缺口；不建设完整聊天副本。
2. **同 Task retry 为首选。** 所有受管 Task 的面板、CLI、自动 retry/stop 在切换执行权前都经过 OSA 持久执行代保护。OSA 不在线就排队或明确拒绝，不能先启动新代后事后检查旧写。该门禁只约束受管 Task，不能把所有 Orca 任务都强制耦合到 OSA。
3. **统一 worker 身份接口。** 由 Orca 核验真实调用者并签发受限证明；OSA 共用入口验证主体，最终领域事务再查当前 assignment、执行代、授权版本和停止标记。内部 launch secret、普通 status 自报字段都不能冒充已实现的接口。
4. **mailbox 后先可靠接管，再业务接受。** 复用同一个 Store 报告记录保存待处理及最终 receipt，不再增加通用队列。同任务报告有明确顺序，不同任务独立消费；在线与补交共用认证和 review 路径。原生批次 ack 代表持久接管，不代表报告已被业务接受。
5. **通知与接续分开。** 只保存无法从 DSH 派生的责任、等待条件、授权动作和消费证据。确认通知不关闭责任；实际决定或续派入库才消费责任。明确动作由现有 pulse 推进，语义决定由持久管理的 Router 处理，空闲唤醒与退出恢复必须实际实现。
6. **完成有输入截止点。** 原生 barrier 与提交同流排序；排空到该位置，再核对输入、授权及停止状态。之后的输入依然可靠登记、显示和续接，不能被上一轮完成吞掉。GitHub/飞书按各自确认水位，不假称全来源原子。用户界面应表达哪些补充仍待处理，不必向用户展示内部序号。
7. **首版不默认增加本地 spool。** 已被 Orca 持久接收的报告必须跨 OSA 停机补交；Orca 不可达则明确失败/unknown，保留责任，不承诺尚未持久化正文可以找回。若扩大到两服务均不可用仍返回可靠 queued，再单独补所需持久入口。
8. **允许有证据的进度合并。** 同任务可合并未发送的进度，保存覆盖关系；不同任务的结果独立可取、独立投递。结果入 outbox 与用户实际看见分别验收，不承诺跨任意外部 UI 的恰好一次显示。

## 实施时不能省略的细节

这些是实现必须满足的约束，不是再开一轮架构选型的理由：

- 所有启动、观察、输入投递、取消、释放和错误回写都核对预期前驱；不只修 `launch` 的一个分支。异步 review 最终提交也检查同一执行代和授权版本。
- 报告固定 ID 必须能在 CLI 超时/重开后恢复，不能每次人工重试换随机 ID。定义并执行同一 Dispatch 的生产顺序及未决请求阻塞规则；不能仅以网络到达顺序声称已经解决旧报告回写。
- 已接管报告不能因临时认证服务不可用被误判永久非法；过期的短期凭据不能抹掉原生已经认证并持久接收的主体证据。已接受回执的历史查询和当前写权限分别验证。
- 不在 SQLite 事务中等待 Orca 网络调用，也不在处理原生 retry 时形成 OSA 等 Orca、Orca 又等同一 OSA lane 的循环等待。持久变更 intent、关闭旧执行代、原生 mutation、安装新回执分阶段恢复。
- 紧急停进程不等于所有业务或外部效果已撤销；明确停止何时被持久接受。旧代失效点是 OSA fence 提交，已发出的外部操作只能对账，不能用超时当作没发生。
- 未归属消息仍须有人处理；只暂停可能受影响的自动完成，能够确认独立的其他任务继续。Router 不可用是可见的责任缺口，不是暗中把完成责任交还用户。
- 迁移从明确的输入起点开始；旧消息来源 unknown、旧回执和在途任务保留。不能通过恢复旧业务库快照撤销升级期间已发生的真实业务效果。

## 有限的交付门槛

采用第三轮报告的五组集成场景，覆盖 T1–T12，不再无限扩展单点实验：

1. 正常 UI 输入、自动化来源、离线跨 epoch、确认前后崩溃及输入截止点。
2. 原生面板/CLI/自动重试与旧 worker 写入竞态，保留同 Task 熔断和资源语义。
3. 混合任务 mailbox 批次、慢 review、乱序/拒绝、接管与业务提交各崩溃点。
4. A 等用户、B 完成并可见、C 按真实依赖接续；通知 ack、Router 空闲/退出及重启不丢责任。
5. 存活但无进度、报告待接受、旧观察、停止和外部效果未知的正确展示与对账。

先实现原生接口与 OSA 适配，再在目标版本真实 IPC/agent 上做隔离 canary，最后统一集成验收及发布。不把新建 Dispatch、唤醒回执、单测数或书面方案当成完整交付。

**最终判断：这次可以冻结实施方向；尚不能冻结“全部需求已满足”的验收结论。** 最难的剩余工作是原生输入契约、所有重试入口的前置保护、真实身份交付，以及 Router 恢复；它们都有指定实现责任和有限验收路径，不能再用 OSA 局部补丁绕开。
