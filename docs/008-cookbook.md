# 008 实践指南

本章承接 [007 架构](007-architecture.md)，逐节对应上游 [008 Cookbook](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/008-cookbook.md)。原版用虚构的 webhook 队列演示新增来源；这里沿用同样的步骤，以 OSA 本地任务评论为例。

状态：2026-11-07，实施说明稿。示例说明如何接入已有领域机制，不代表插件、接口和测试已经实现。原版 `SourceKind`／`SourceContext` 的宿主 API 不能直接当成 OSA 现成接口。

## 添加一个来源

对应上游：Add a Source。

一个来源需要完成事件翻译、准入、上下文和回复。下面的步骤用于说明责任，不是要求实现十一层函数；本地入口能在一个函数中清楚完成的逻辑就近写，已有能力直接调用。

本例的入口是所有者在 OSA 面板中的任务请求与评论。它通过插件连接 OSA 服务，服务写入同一份工单记录。Agent 结果从现有报告和回复路径返回，不为面板另建一套任务系统。

本地提交是事件请求，不需要模仿 webhook 额外启动一个轮询器。GitHub、飞书等远程来源继续使用其实际接收方式。

### 1. 把事件映射到领域

对应上游：1. Map the events onto the domain。

先明确身份及关系，再写入口代码。编号和回复位置会持久保存，不能随着页面切换或标题修改重新生成。

| 概念 | 本地任务评论的对应 |
| --- | --- |
| Trigger | 一次已提交的原始请求或评论；保留稳定消息编号 |
| Thread | 一条请求及其持续讨论；任务页使用已经关联的话题 |
| Actor | 实际作出操作的所有者身份，不采用正文里自称的身份 |
| Channel | 回复应出现的项目、话题或任务位置 |
| 接收范围 | 当前服务已接入的项目及明确关联的工作 |
| 项目／仓库 | 工作归属与执行定位，不自动变成新授权 |

新请求尚无工单编号时，可以先有稳定的话题身份，接单后记录其与工单的关系。后续评论使用这个关系，不因用户从全局视图切换到项目页就创建新话题。

一个项目里的全部任务不能共用一个无区分的讨论串。跨入口引用已有任务时保留原消息，再按授权与路由规则关联。

### 2. 配置、字段、事实与健康状态

对应上游：2. Configuration: schema, fields, facts and health。

原版来源声明配置校验、设置字段、账号事实和健康状态。OSA 保留这些责任，但先复用现有配置与校验方式，不要求为一个本地入口引入完整动态表单框架。

本地入口至少需要知道连接哪一套 OSA 服务、当前项目，以及消息实际来自谁。已有配置可确定的信息直接读取，不要求用户每次填写。

配置错误显示实际问题。面板未连上服务不能显示“没有任务”，保存到页面缓存也不能显示“已接单”。健康问题由产生它的部分维护，不把瞬时失败变成重复广播。

外部来源的新配置默认只接收明确设置的范围。账号身份用实际检查结果显示，不信任用户界面随意填写的“已验证”标记。

### 3. 把消息转成 Trigger

对应上游：3. Translate a message into a Trigger。

外部请求在 OSA 服务接收入口完成一次必要的格式、来源与目标校验，转换为明确类型后使用现有 `Engine.receive`。插件 worker 只转发，不再复制同一校验；内部 App、核心和辅助函数不重复解析相同字段。以下只是核心记录的示例，不是已经提供的面板 API：

```json
{
  "id": "panel:message-001",
  "source": "panel",
  "actor": { "source": "panel", "id": "owner-id" },
  "human": true,
  "addressed": "direct",
  "threads": [{ "source": "panel", "id": "request-001" }],
  "at": "2026-11-07T02:00:00.000Z",
  "text": "修复导出文件的日期显示",
  "channel": {
    "source": "panel",
    "thread": "request-001",
    "address": { "projectId": "project-a", "threadId": "request-001" }
  },
  "meta": { "projectId": "project-a" }
}
```

示例中的 `owner-id`、`human` 和 `direct` 由接入层根据实际操作确定，不能把客户端提交的任意身份当成事实。这是正常的入口校验，不建立同用户进程间的新认证体系。

同一次提交重试使用相同编号；实际编辑作为新的修订保留，不覆盖已经记录的原事件。响应不明时先查询或重放同一请求，不能生成新编号反复提交。

只有实际发送的内容成为事件。草稿不是请求；展示 Agent 已有回复也不能再生成一条“所有者请求”，否则会形成自我接单循环。

`projectId` 帮助定位，正文表达要求；真正的工作授权仍由准入与路由形成。保存一条事件不等于立即开始修改代码。

### 4. 来源接收什么

对应上游：4. What the Source receives: scope。

沿用原版的区分：来源范围决定哪些事件进入处理，Policy 决定谁可以发起工作，Mandate 决定本次可以做什么。

本节补充上一节入口校验中的范围规则，不增加第二个校验阶段。入口一次确认项目及任务／话题归属，内部使用所得目标；不明确时保留原请求并澄清，不根据当前窗口猜测。

来源范围检查不靠分析正文里的仓库名。外部来源使用实际的账号、仓库、群和话题元数据；过滤结果保留原因，不悄悄丢弃。

当前 `App.inScope` 主要支持 Router、GitHub 和飞书。接入本地来源需要补充对应处理，不能把所有插件消息伪装成已经核验的 Router 人工输入。

### 5. 回复：Channel

对应上游：5. Replies: the Channel。

复用 Outbox 的消息身份和发送结果。面板展示已有回复，或接收服务返回的新回复；重新打开页面不能再次执行回复动作。

| 情况 | 处理 |
| --- | --- |
| 确认接收并保存了回复 | 记录实际成功结果 |
| 面板暂时关闭、服务连接中断或来源暂时停用 | 保留消息；不把临时不可用标成目标已消失 |
| 已确认目标永久不可接收或不再属于监听范围 | 保存丢弃原因及原消息关系 |
| 发送结果不明 | 按原消息身份核对，不直接重复发送 |

原版的 `sent`、`gone`、等待与异常结果，应映射到 OSA 实际发件箱语义，而不是只复用单词。GitHub 或飞书具体的去重方式由对应适配器承担。

任务表显示的是相同业务记录，不能把一次结果同时写成几条互不相关的通知。向外部渠道增加反馈去处，需要有明确的登记与依据。

### 6. 供评估使用的话题上下文

对应上游：6. Thread context for assessments。

提供原始请求、被回复的消息、相关补充和已有工单摘要。内容长时分页展开，保留消息编号、作者、时间与回复关系。

即使第一版不启用主动接单，明确请求的归属判断也需要这些上下文。只给 Router 一句孤立的“可以”，它无法知道所有者回答了哪个问题。

本地已保存的消息优先从 Store 读取。需要外部原文时由来源读取，不让 Router 为理解请求自行调查代码、设计方案或扫描所有项目历史。

内容尚未读取或无法获取时如实标明。链接存在不证明正文已经被理解，摘要也不能替代被截断的关键限制。

### 7. 谁可以提出工作

对应上游：7. Who may ask: the Source's part of the Policy。

沿用个人所有者准入，调用已有 Policy 完成同一次入口处理中的资格判断，不在后续每层重复检查。新增来源只增加实际映射，不增加项目管理员、组件管理员或多仓库审批。

所有者的新请求可以接单；已有任务的补充按订阅和范围规则处理。机器人和审查结果可以提供反馈，不能自行扩大授权。

来源接收范围与 Policy 使用的范围必须一致。能查看一个项目不自动授权修改其中全部仓库；同样，执行已授权目标涉及多个仓库，也不因此增加一层特殊权限。

在插件里点击“重新评估”等人工操作，与 Router 日常路由分开表达。当前 Router 租约不能被当成所有者界面的通用操作身份。

### 8. 给执行者的环境信息

对应上游：8. Variables for the Executor。

沿用第三章的执行环境内容：工单、派工、项目、相关仓库、实际目录、原请求、回复位置和已有交接。多仓库逐项说明，不让默认目录覆盖真实目标。

使用现有工单读取、交接文件或原生上下文传递这些信息，不要求每个新来源发明一套环境变量。信息含义与实际工具一致，不放入凭据值。

背景知识保留范围和来源。另一项目的一条工程事实不能自动成为当前工作的限制或授权。

### 9. 插件入口及接收过程

对应上游：9. The plugin entry and its loop。

原版示例使用来源插件和轮询循环。OSA 的本地评论按实际入口接入：

```text
所有者发送评论
  → Orca 插件将原始请求交给 OSA 服务
  → 服务校验来源，保存事件，调用现有领域流程
  → 需要路由时通过原生事件唤醒 Router
  → 需要执行时通过 Orca 投递给相应执行者
  → 报告与回复回到原任务记录
```

箭头表示处理过程，不要求每一层再建消息队列和确认协议。业务只复用必要的已有结果：服务是否保存、原生是否接收、执行者报告了什么。页面不能从提交成功跳到“Agent 已完成”。

面板和插件 worker 的生命周期服从 Orca；业务待办保留在 OSA。插件重载后重新读取状态，不依赖插件内存里的计时器维持任务责任。

远程来源若需要轮询，沿用原版要求：准备完成后运行；事件保存后才推进读取位置；单项错误保留并继续处理无关项；退出时停止自己的循环。无需为本地任务评论额外增加轮询器。

关闭面板、删除草稿或切换项目不等于关闭工单。来源生命周期只有明确的业务含义时，才通过核心接口影响任务结束，例如已绑定 PR 的关闭事件。

### 10. 注册与接入

对应上游：10. Register the plugin。

原版把来源加入 DSH 的构建入口、导出和插件配置。OSA 使用 Orca 插件及现有本机服务，因此不能复制其 `cordis.patch.yml` 安装步骤。

实现时需要覆盖的接入点是：

| 接入点 | 应做的事 |
| --- | --- |
| Orca 插件声明 | 声明面板、worker、实际需要的能力与兼容版本 |
| 插件请求处理 | 转交具体的任务读取、消息提交和人工操作，不开放任意命令执行入口 |
| OSA 应用入口 | 校验本地来源、身份、项目及话题，调用现有核心接口 |
| 回复路径 | 将同一业务回复提供给任务页，并保留状态和来源 |
| 配置与查询 | 展示实际连接和处理结果，不让每次查询抢占 Router |
| 文档与检查 | 更新模块索引、命令说明和对应测试 |

当前 `App` 中的来源识别、范围检查与命令处理，以及 `bin/osa.ts` 的运行组装，是实际接入位置。先就近完成这条路径，不为每个步骤抽 helper 或预建 SourceRegistry。错误只在能处理的入口或资源边界捕获，其余向已有错误出口传递。

插件先做离线校验和测试，再按 Orca 的实际能力批准流程加载。插件可被加载不等于业务接入已验收；正式启用还需验证真实请求、执行和反馈。

### 11. 测试

对应上游：11. Tests。

沿用原版方式：临时 Store、真实 Engine、来源输入和可控外部替身，验证事件怎样变成工作及回复。不要只测试一个函数返回成功。

| 场景 | 应验证的结果 |
| --- | --- |
| 同一消息提交两次 | 只保存一个原事件，不重复接单 |
| 同一编号却有不同正文 | 明确拒绝或按修订协议处理，不悄悄替换原请求 |
| 对已有任务补充 | 原执行者收到输入；范围内继续，范围外交回 |
| 项目归属不匹配 | 不投到错误任务，原请求和原因仍可查 |
| Agent 回复展示与页面刷新 | 不被误认为所有者新请求，不重复回复 |
| 服务保存后响应丢失 | 使用同一请求身份能够核对结果 |
| 来源暂时关闭与目标永久消失 | 等待与丢弃有不同结果，原记录保留 |
| 用户回复“可以” | 能找到它所回答的问题，不推导为全部授权 |
| 插件重载或面板重开 | 重新取得同一工作状态，未发送草稿不被提交 |
| 多项目并行 | 请求、执行位置、结果和回复不串项目 |

再用实际插件和 Agent 完成一条工作循环，验证后台唤醒、任务内补充和原处交付。使用临时目标，不为了写测试触碰真实生产或发送无关外部消息。

2026-11-07 已实现 `panel` 来源、所有者接口及原生插件。模拟测试与真实宿主工作循环分开记录；具体结果见本轮验证记录。不为穷举理论并发、取消和崩溃时机扩展生产机制。

### 检查清单

对应上游：Checklist。

1. 事件、话题、发送者、回复地址和项目范围映射明确。
2. 具体配置可检查，错误不会被展示为空数据。
3. 外部数据在接收入口校验一次，内部使用类型；原始事件编号稳定，自身回复不重新接单。
4. 接收范围与授权依据分别处理，归属不靠关键词猜测。
5. 回复沿用同一消息身份，临时失败与永久不可达有区别。
6. 原文和回复关系可读取，截断内容可展开。
7. 新来源沿用所有者准入及范围内继续、范围外交回规则。
8. 执行环境指向实际项目与仓库，不包含凭据值。
9. 待办保存在服务，插件重载不承担业务恢复责任。
10. 接入覆盖实际需要的入口、回复和查询；单次逻辑就近内联，不提前建框架，不改 vendor 或 Orca 本体。
11. 自动检查与真实工作循环分别验证，差异和限制如实记录。

同样的方法可用于其他真正需要的来源：先完成它与现有领域的对应，再补最少的适配。不要因为新增一个入口，就复制一套 Router、工单库或执行调度器。
