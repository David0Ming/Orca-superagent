# Orca 插件化可行性验证

2026-11-04。**建议将 OSA 作为独立插件产品交付，复用现有业务服务；但在保留“原生聊天直接追加要求、原生面板重试也正确”等要求时，当前公开插件接口不足以独立保证全部需求。** 优先争取 Orca 提供通用、版本化的可靠性扩展接口，而不是长期维护塞入 OSA 业务逻辑的 Orca 分支。接口若被上游正式接纳，日常升级就不需要反复合并私有宿主补丁；目前没有上游接纳承诺。

这修订的是上一轮的交付和扩展方式，不撤销已确认的输入、身份、接续和报告可靠性要求。称为“插件”本身不会让缺失的宿主能力出现，也不能保证未来 API 永不变化。

## 版本与来源

- 本机 CLI 路径是 `/Applications/Orca.app/Contents/Resources/bin/orca`；安装元数据与运行时均报告 **1.4.247**，build commit `ec7da75d4f372ea3270864d3e2b8d0ba1efcee5d`。前轮原生实验用的是 1.4.227，不能直接把旧版本的能力清单套到现在。
- 当前本地 Orca 源码工作树 HEAD 仍是旧提交，因此本次关键实现从上面精确公开提交读取并归档，没有用旧工作树冒充安装版本源码，也没有改动该工作树。
- 读取安装版 `orca-plugin-authoring` 及 host-api、events、recipes、cli 参考；官方公开 [插件说明](https://www.onorca.dev/docs/settings) 也确认独立 worker 和插件安装机制。
- 该构建附带的指南把部分 hooks/API 标为 Since 1.4.248，尽管运行时版本为 1.4.247。离线 manifest 验证和源码已有实现不等于启用后的完整兼容性。本次没有降低最低版本或启用插件来绕过它。

## 哪些可以放进插件

- 面板、任务和状态展示、设置、操作入口、任务级结果展示。
- OSA 的领域处理、输入归属、授权修订、报告 receipt、接续责任、现有 DSH 核心。Node worker 可运行这些代码；持久业务事务继续使用已有 SQLite Store，不为迁移插件而换成一组无事务的 storage.get/set。
- 通过现有 CLI/API 使用 Orca 的工作区、Task/Dispatch、retry、mailbox 和资源观察。Host API 未封装的 CLI 能力可由 trusted worker 的 Node 进程调用；“SDK 没列出”不等于插件不能调用任何 CLI。
- 用插件 bridge 连接现有 OSA supervisor/服务。插件面板或 worker 的临时退出不应消灭持久业务责任；无需重写已有服务来迁就插件生命周期。

插件 worker 具有用户账户的本机权限，打包业务逻辑和调用 CLI 可行；但这种权限不等于稳定的宿主事务接口。直接读写 Orca 私有数据库、patch app.asar、注入宿主模块或 monkey-patch 都没有解决用户担心的升级耦合，不作为推荐实现。

## 现有接口不能覆盖的边界

### 1. 原生聊天输入的可靠接管

公开 worker 事件只有工作区创建/删除/切换及 agent 状态变化，没有可靠用户提交流、确认水位或完成 barrier。事件投递实现启动 worker 后直接投递；失败记录 dropped，没有这里所需的持久重放契约。

`agent.prompt.before`/`terminal.send` 明确排除人的 desktop/mobile 输入，它们用于程序发送的提示，不能拿来保证用户在普通聊天补充的要求全部登记。该行为由[当前提交源码](https://github.com/stablyai/orca/blob/ec7da75d4f372ea3270864d3e2b8d0ba1efcee5d/src/main/runtime/terminal/input/terminal-send-plugin-hook.ts)及隔离检查共同证实。

当前提交的 journal rollover 仍调用 `deleteJournalEpochRows` 删除旧 epoch；本轮只复核源码，没有重跑新版本的跨 epoch 原生实验，也没有据此断言不存在其他副本。现有插件接口仍未提供“消费确认前保留”的保证。

### 2. 当前执行身份与所有重试路径的前置保护

现有 [hook 集合](https://github.com/stablyai/orca/blob/ec7da75d4f372ea3270864d3e2b8d0ba1efcee5d/src/shared/plugins/contributions/plugin-hook-contribution.ts) 没有 Task/Dispatch retry、stop 或业务写入前置事务钩子。`agent.launch.before` 可以改启动命令和增加环境变量，但排除保存会话恢复等路径，载荷也不是完整 Task/Dispatch 权威证明；它不等于在原生执行代切换之前原子撤销旧业务权限。

钩子可以配置 `onError: deny`，所以不能笼统说“所有钩子失败都放行”。但插件被禁用、移除或变更时，参与者会退出钩子链；这与“受管任务的保护不因插件暂不可用而消失”的要求不同。还没有公开接口提供上一轮方案需要的 worker 受限证明及全入口执行代门禁。

通过一个启动钩子注入 OSA 自有 token，可以覆盖部分受控启动，不能未经验证就外推到原生面板 retry、会话恢复和所有运行模式。

### 3. 持久推进与事件送达

官方指南说明空闲 worker 会停止并由下一条命令/事件/request 激活；源码默认崩溃重启预算也有上限。插件状态事件是观察信号，不是持久业务日志。应继续复用 OSA 服务、持久 job、原生 mailbox 和重启对账，而不是把全部监督改成插件里的内存 timer。

这不是说插件不能进行后台计算，而是不能将现有生命周期未经验收当作持续业务推进的保证。

## 推荐交付方式

**首选：OSA 插件 + 现有持久服务 + Orca 通用扩展契约。**

1. 插件负责 UI、设置及集成入口，业务核心保留在独立 OSA 模块和服务中；继续原样复用 DSH。
2. 向 Orca 提交最小通用接口需求：可靠提交事件流及确认/截止点、原生执行主体证明、受管 Task 变更前置门禁。这些接口属于宿主可靠性能力，不包含 OSA 业务状态机。
3. 用版本和能力协商适配，保留公开 CLI 边界及针对目标版本的契约测试。所需能力缺失就明确显示不支持，不能退回读私库或默默放弃保证。
4. 最终仍执行第三轮的五组组合验收，额外包含插件升级/重载/禁用及 OSA 服务退出时的持久责任处理。插件测试框架通过不替代真实 IPC/agent canary。

这种方式能降低维护私有 Orca 分支的需要；真正消除私有补丁需要这些通用接口进入上游正式版本，不能现在就保证上游会接纳或升级永不失效。

**严格零宿主改动的备选**：把输入、补充、停止、重试全部收敛到 OSA 自己的插件面板/命令入口，由 OSA 先持久接收，再驱动执行。这样可以避开部分原生输入缺口，但会改变用户操作方式；原生聊天补充和原生面板 retry 仍不能自动享有相同保证。若仍允许从这些旁路操作，必须有明确受管边界与核查，不能称为原需求已全部满足。本轮没有替用户接受这种需求缩减，也没有验证这一替代流程的完整实现。
