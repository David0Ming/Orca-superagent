# 005 面板

本章承接 [000 理念](000-philosophy.md) 至 [004 提示词](004-prompts.md)，按上游 [005 Panel](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/005-panel.md) 的全部小节顺序，说明个人多项目下应看见什么，以及如何继续工作。

状态：2026-11-06，所有者认可本章的信息结构和操作方向。沿用 dsh 的信息与操作原则，按已确认的“项目任务表为主入口、任务内对话”调整导航。页面、抽屉或标签的具体实现尚未确定；本文不代表 Orca 已经提供这些界面。

## 三个问题

对应上游：Three questions。

打开面板，按原版的顺序回答：

1. **现在有什么需要我？** 哪个任务需要回答、查看结果或处理实际阻碍？
2. **工作是否在正常推进？** 各项目在做什么，哪些等待、失败或状态未知？
3. **这件事是怎样走到这里的？** 原始要求、补充、路由、执行、结果都能追溯吗？

全局视图帮助分配注意力，项目视图帮助了解一组工作，任务视图帮助继续具体事情。用户不必依次打开所有 Agent 窗口才能回答这些问题。

## 页面与导航

对应上游：Tabs。

原版按 Overview、Source、Trigger、Eval、Execution、Settings 组织。OSA 保留这些信息的归属与可查性，并以个人日常使用顺序组织入口。

| 原版页面 | OSA 中的对应位置 | 保留的信息 |
| --- | --- | --- |
| Overview | 全局总览 | 待决事项、可用结果、系统问题及必要的执行负载 |
| Source | 来源管理与相关异常详情 | 账号和接收范围、连接状态、过滤和发送失败的原因 |
| Trigger | 任务对话及消息记录 | 原消息、所属话题、处理去向；未关联任务的消息也能查到 |
| Eval | 任务的路由记录及未处理请求 | 接受、关联、停止或忽略的依据，评估未完成的原因 |
| Execution | 项目任务表及任务详情 | 任务阶段、授权、待处理输入、当前与历史执行 |
| Settings | 设置 | 来源、准入、执行、提示词和运行配置 |

全局、项目和任务是同一份数据的不同视图，不各自维护一套进度。来源、消息、路由等记录可以在详情中展开；不会因为简化导航就删除它们。

**全局总览。** 优先展示需要所有者处理的事项：具体问题、可查看的结果、需要介入的异常。每项标明项目和任务，并直达相关位置。正常工作提供简短摘要；没有问题时，不铺满“健康”“正常”的卡片。

**项目任务表。** 项目下展示该项目的工作，并提供提出请求的入口。任务行首先回答“是什么事、到哪了、下一步是什么”。

| 默认信息 | 用途 |
| --- | --- |
| 任务名称 | 识别希望完成的结果 |
| 当前阶段及原因 | 说明在推进、等谁或因何受阻 |
| 最近进展 | 最近一次有实质内容的更新 |
| 负责执行者 | 能找到当前执行窗口；多个协作者按需展开 |
| 更新时间 | 判断信息是否新鲜；不把时间变化冒充进展 |
| 当前需要的动作 | 回答问题、查看成果或其他明确操作；无须行动时留空 |

项目已经由页面选定，不要求每行重复填写项目字段。一个项目涉及多个仓库时，相关仓库在任务详情中显示；同一业务工作不因开了多个窗口而重复出现在列表里。

**任务详情。** 先显示目标、当前结果或问题，再显示持续对话。所有者在这里补充要求、回答问题；Agent 在同一工作记录下回复。成果、相关仓库和原执行窗口提供直接入口；授权和历史派工等细节可展开。

提出请求和评论继续走 [002 授权](002-authorization.md) 的原版规则，不在界面增加另一套开始审批。范围内补充交给原执行者，范围外的新请求交回 Router。若因此建立新工单，保留与原请求的关系，不让用户重新输入已说过的话。

**全局聊天。** 作为辅助入口查询状态、提出要求或澄清归属。确定归属后指向相应任务；不会成为唯一保存任务进度的地方。

**直接使用 Agent 窗口。** 所有者可以打开关联窗口查看细节或直接交流。面板应显示窗口与任务的实际关联；尚未关联的窗口不能被静默猜成某个任务。关联操作不新增执行授权，双向消息接入是否完整仍需验证。

初次使用缺少必要账号或执行环境时，沿用原版做法，显示缺失项并直达相应设置。不要把尚未配置、来源失联或确实无任务，都显示成同一个空列表。

### 查看单条记录

对应上游：Reading individual records。

单条记录沿用原版的可追溯关系：从请求能找到路由依据和任务，从任务能找到原始授权、后续输入、报告及执行记录。内部编号可展开，日常先显示可识别的名称和内容。

消息分别说明以下事实，不使用一个“已完成”包办全部含义：

| 显示 | 能证明什么 |
| --- | --- |
| 已保存／待处理 | 系统保留了输入，尚不代表执行者收到 |
| 已投递 | 输入已经送到对应执行入口，尚不代表读到或处理 |
| 已读取 | 有实际读取依据，尚不代表工作完成 |
| 已处理 | 有对应答复、处理说明或交回结果 |
| 投递失败／已丢弃 | 原因、时间和相关任务可查，不能标为已通知 |

报告说明业务进度，原生执行记录说明窗口或进程状态，两者分别显示。例如“任务等待答复，执行已结束”可以同时成立；窗口仍被保留不能被写成任务仍在运行。

操作沿用已有语义，按当前状态提供：

- **回答问题：** 在引出问题的位置回复，保留对应关系，未发送草稿不算答复。
- **查看结果：** 打开实际成果、PR 或验证证据；草稿与就绪结果明确区分。
- **打开执行窗口：** 导航到对应会话，不把它隐含为重新启动工作。
- **重试：** 用于符合条件的投递失败、受阻或失败任务；依照执行章和原生回执恢复，不能在状态未知时凭按钮点击重复派工。
- **重新评估：** 沿用原版的人工纠正入口，查看并重新判断尚无有效处理结果的请求。Router 的日常路由权限不能借此越过仍在负责该消息的执行者。
- **停止：** 明确停止的是哪件工作并保存决定。不能因为停止一张任务，误停整个项目或其他窗口。

按钮必须有实际接口支撑。尚未实现的动作不做成看似可用的操作；失败保留输入和原因。对于需恢复、需接管或需释放的资源，展示真实可执行的下一步，不统一显示“点继续”。

用户改标题、查看报告、拖动列表顺序，与改变授权、业务状态或运行优先级不是同一动作。只有实际执行了相应操作，才更新对应事实。

## 设置分组

对应上游：Settings groups。

下表用于对应原版设置职责，不是五个必须新建的设置页面。第一版只呈现当前确实需要、且已有实际能力支撑的配置。

| 分组 | OSA 应表达的内容 | 边界 |
| --- | --- | --- |
| 来源 Sources | 已接入账号、监听的群或仓库、项目关联、实际连接问题 | 来源实例与项目分开；不强制每项目一个飞书群或独立实例 |
| 评估 Eval | 所有者身份、当前准入和主动接单模式 | 第一版以所有者明确请求为基础，不扩展团队成员管理 |
| 执行 Execution | 实际模型、执行容量、工作目录及已有执行配置 | 区分业务工作槽与原生资源状态；同一配置只有一个权威来源 |
| 提示词 Prompts | 沟通、工作范围、交付约定、技能及有效版本 | 按提示词章说明已保存与已生效；不假装已有逐请求热更新 |
| 部署 Deployment | 服务是否可用、状态目录、当前加载版本和实际运行问题 | 不因保存成功就声称服务已应用；按真实能力提供检查或生效操作 |

配置先展示实际值和保存结果，失败保留输入。已有文件或宿主提供历史时直接使用，不为复制原版先建提示词差异面板、并发版本锁和通用动态表单。

只读状态与可编辑配置要清楚区分。某项设置由 Orca 或 Agent 自己管理时，优先展示实际值并指向原生入口，不维护第二份互相覆盖的配置。

## 搜索

对应上游：Search。

沿用原版按内容、消息编号、话题引用、工单标题及原始链接查找的方式。已存记录应能找到，尚未接入或未索引的内容不冒充已覆盖。

OSA 增加项目范围：在项目内默认查本项目，全局搜索跨项目并显示每条结果的项目归属。相同标题不能自动合并，单独的 `#12` 在多仓库下也不能被当成唯一定位。

结果首先显示匹配的任务、原消息或成果，并给出可继续工作的入口。存在多个合理结果时供用户选择，不能凭搜索排序最高就把新要求附加过去。

Orca 的完整会话搜索可作为已关联窗口的补充；只有原生索引实际可用时才使用。任务查询本身不应依赖扫描用户全部聊天、文件或窗口。

## 原则

对应上游：Principles。

逐项沿用原版七条原则：

1. **聚焦需要人的信息。** 每个元素服务于开头的三个问题。数字能帮助判断或操作才显示；不把 Agent 数量和消息数量当成产品成果。

2. **状态定义明确。** 当前业务阶段按执行章判断，说明等谁和等什么。执行状态、投递状态分别表达，缺失或过期的信息如实标明，不用同一个颜色暗示所有含义。

3. **每类事实有一个归属。** 来源配置归来源，原消息归话题，路由依据归决定，任务结果归工单。总览和项目页读取这些记录，不成为另一套手工维护的进度表。

4. **结构遵循领域。** 用户先看到项目和任务，内部术语和编号按需展开。仓库、分支和窗口在需要定位执行时出现，不要求用户把它们都当成项目。

5. **状态诚实一致。** 计数必须等于对应范围的列表项数，并使用相同时间窗口。报告就绪、PR 已合并、线上已部署是不同事实；不能用“窗口完成”替代业务完成。

6. **默认安静。** 不为每次进度变化发通知；可自动恢复的瞬时错误不要求用户立即处理。真正需要人时直接给出相关内容与操作。沿用原版对破坏性界面操作的明确确认，不另加任务开始或已授权步骤的二次审批。后台更新不得覆盖、提交或挪走用户未发送的草稿。

7. **操作方式一致。** 在 Orca 内接入时沿用其已有组件和交互习惯，同一信息在不同页面使用相同含义。状态有文字说明，常用操作可通过键盘到达；保存、失败和重试的反馈保持一致，不要求用户猜测是否已经发生。

当前只确定信息结构和行为。具体接入 Orca 的方式、可用原生组件以及新增界面的运行位置，需后续核验；不新增 Orca 本体修改，也不因为旧方案写过“不做面板”就否定本轮已确定的任务表入口。
