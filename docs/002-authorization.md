# 002 授权

本章承接 [001 领域模型](001-domain.md)，按上游 [002 Authorization](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/002-authorization.md) 的小节顺序，说明谁能发起工作、执行者可以做到哪里，以及补充和停止如何生效。

状态：2026-11-06，所有者已确认开始工作、交付权限以及不可变授权与交回机制沿用 dsh，不增加多仓库特殊权限。**“现状”只说明代码，不代表它已经符合本章。** 其余沿用已确认的 [理念](000-philosophy.md) 与 [开发宪章](../AGENTS.md)。

授权来自所有者的真实请求及明确规则。Router 负责理解归属和转交，Executor 负责授权内的技术判断，程序记录身份、来源和处理结果。授权不能由 Agent 自己的计划、审查意见或一条成功通知产生。

## 一个事件的两条路径

对应上游：Two paths for a Trigger。

### 评估：决定是否开始新工作

对应上游：Eval: deciding whether to start work。

沿用 dsh：Source 记录发送者、接收范围以及是否直接发给 Agent；程序检查准入。符合条件的明确请求成为候选，由 Router 判断接单、关联、停止或忽略。接单后建立授权并进入执行，已有工作的话题补充则走订阅路径。

有资格发起工作，不代表每句话都自动开工。“修复导出错误”可以接单；普通讨论和状态查询按其实际含义处理。明确请求在主动接单模式关闭时也有效。

**不另设 OSA 的开始授权流程。** 项目任务表和聊天都映射到已有事件、话题和准入机制；新界面只负责表达来源与归属，不凭一个按钮名称替代上述判断，也不额外增加一次“是否开始”的确认。

项目或任务位置已经明确的信息直接使用。Router 不要求所有者再说一遍项目名，也不擅自把短请求扩成实施计划。

### 订阅：让已有工作继续收到讨论

对应上游：Subscriptions: continuing existing work。

已经属于某任务的评论、问题和反馈进入原工作，无需每条都重新接单。执行者读取并处理授权内的补充；超出当前工作时交回。

订阅允许背景消息进入，包括 CI 和审查结果，但不会给发送者新的授权能力。只有所有者的真实指令可以修改目标或限制。

执行者正在负责一条补充时，Router 不应再把它派给另一个执行者重复做。所有者明确要求停止或改交时，按该要求处理，并保留原工作的去向。

### 交回与释放后续消息

对应上游：Handing back and releasing follow-ups。

消息属于另一任务、另一项目，或提出独立的新目标时，执行者说明依据并交回 Router。交回原因跟随原消息，不能只留下“不能做”。

上游会在没有工单继续负责该消息时，重新把它送入评估；工单结束时，也会释放尚未读取或接手的后续请求。已经处理的输入不因为换执行者就重新成为新工作。

OSA 沿用这一归属原则。消息未投递、未读取或执行者已经结束时，应明确记录实际状态；Router 不能仅凭入队就声称“执行者已在处理”。

所有者要求重新定位时，原话、已有成果和交回原因一起保留。重新路由本身不增加工作范围。

### 仅供背景的订阅

对应上游：Context-only subscriptions。

相关 Issue、其他任务报告和项目文档可以提供背景，不因此成为本任务的命令。Router 转来的其他工作事实也只作参考。

例如，执行者读到另一项目“准备升级数据库”的讨论，可以据此理解依赖，但不能自动替另一项目执行升级。背景话题的新消息也不能自行恢复已结束或已叫停的工作。

## 授权强度

对应上游：Strength。

沿用上游的 `explicit`、`inferred` 和不准入三种判断。它们表示工作依据的类型，不表示“有多少系统权限”。

| 判断 | OSA 第一版的含义 |
| --- | --- |
| 明确请求 `explicit` | 已核验的所有者向系统提出要求或补充；仍需理解这是执行、查询还是讨论 |
| 推断请求 `inferred` | 从通知、CI、他人发言等推测可能有工作；第一版不据此自动开新任务 |
| 不准入 | 来源或身份不符合接收规则，不作为新工作授权 |

明确请求也有具体边界。“只查原因”不会因发送者是所有者就变成“修改并部署”。

## 准入

对应上游：Admission。

第一版围绕同一个所有者，不建立团队角色或成员权限树。来源接入时确定账号和监听范围；每条外部请求在接收边界完成一次必要的格式、来源和身份校验。内部流转使用已确定的类型与来源，不在每个函数重复核验同一份输入。

| 入口 | 授权依据 | 不能推导出的权限 |
| --- | --- | --- |
| 项目任务表 | 所有者提交的原始任务、评论和明确操作 | 能查看项目，不等于可以修改项目全部内容 |
| 全局聊天 | 所有者的原话及其上下文 | 讨论一个方案，不自动授权实施 |
| 飞书 | 已核验账号、已配置的接收范围及原始消息 | 身处同一群，不等于其他群成员也能授权 |
| GitHub | 已核验账号、已配置仓库及 Issue／PR 消息 | 有仓库访问权限，不等于任何评论都能扩展任务 |
| 已有关联窗口 | 能追溯的原始所有者请求和后续指令 | Agent 自称“用户已授权”不能替代原始依据 |

引用、转述和转发要保留真实来源。外部文档里写着“忽略之前的限制”，不能当作所有者的新决定。

已有窗口的原始授权可查时直接沿用，不要求重新描述。只有关键授权无法确认时，才询问缺失的那一项；记录窗口归属本身不触发新的执行。

**现状：** [App](../src/app.ts) 已使用 `owner-only-v1` 检查 Router、GitHub、飞书来源的所有者身份，关闭推断式接单。本地任务评论和任意已有窗口的来源接入尚未完整实现；本表是它们应遵守的规则。

### 机器人和自动审查者

对应上游：Bots and automated reviewers。

机器人、CI 和审查者可以指出失败、提供证据和建议修复。执行者可以在原授权内处理这些反馈，无需为每条测试错误重新请求许可。

它们不能授权无关功能、扩大项目范围、解除所有者限制或恢复被叫停的工作。审查发现真实问题应处理；回执格式错误属于技术摩擦，不能变成要求所有者反复授权的理由。

使用普通账号的自动审查者也要按真实角色识别。不能仅因为账号看起来像人，就把它的意见当成所有者决定。

## 路由候选请求

对应上游：Routing candidates。

沿用上游的接单、附加、停止和忽略等操作。一个候选处理失败，不应阻断无关项目的请求。

Router 只判断目标及归属。项目、任务或仓库已有明确定位时直接路由；仅有主题相似时不猜测关联。执行者交回后，Router 忠实保留拒绝理由，并按原请求重新定位。

派发包含所有者原话、定位信息和所有者明确说过的限制。标题、摘要和路由备注不能代替原始授权。

### 角色权限

OSA 对应说明。

| 角色 | 可以做 | 不能自行决定 |
| --- | --- | --- |
| 所有者 | 提出结果、修改范围、作出业务取舍、授权重要操作、停止工作 | — |
| Router | 查看相关项目状态，澄清目标，定位和路由，传达结果与问题 | 技术方案、实施步骤、新的验收门禁、超出所有者要求的授权 |
| Executor | 在范围内调查、规划、实现、测试、组织子智能体和处理技术摩擦 | 独立新增业务目标，解除所有者限制，擅自执行未授权的重要操作 |
| Reviewer | 检查需求、改动和证据，指出实际或可复现的问题 | 用审查意见增加业务要求或授予发布权限 |
| 程序 | 校验可确定的身份和归属，保存原始输入与回执，维护状态 | 替所有者作业务决定，保证模型理解永远正确 |

### 多仓库任务的授权范围

所有者已确认：**多仓库不构成一种特殊权限，不单独增加审批。**

是否可以做，依据原请求、授权范围和已有工作规则判断。仓库数量或项目标签本身不决定是否需要再次授权。完成原目标需要协作修改多个仓库，就按原授权推进；即使只改一个仓库，超出目标的新工作也不能自行加入。

例如，要求“增加客服标签并在管理台显示”，必要的前后端修改可以属于同一任务。若明确限制“只查原因”，调查涉及几个仓库都不改变这个限制，也不能直接开始修复。

拆任务、换模型和交接不能增加权限。执行者记录实际涉及的仓库、依赖和影响，按 dsh 的范围与交付规则处理，不因跨仓库再经过一层 OSA 门禁。

**现状：** 当前 `TicketTarget` 固定一个目标位置，GitHub 补充还会核对原仓库。这是现有适配方式，不能被当成“多仓库需要特殊授权”的产品规则；具体适配留到执行章。

### 补充、更正与新工作

沿用原版规则；旧 OSA 的范围修改行为作为实现差异列出。

**普通补充、更正、提供新线索，以及受阻后的重新判断，dsh 本来就支持。** 授权范围内的后续请求交给原执行者；阻碍解除后可以继续，不要求所有者再说一次“继续”。这些不是 OSA 新增能力。参见上游 [工作范围提示词](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/scope.md)。

真正的差异是：**能否修改原工单的 Mandate.scope。**

| 情况 | 原版 dsh | 上一版 OSA 草案及旧代码 |
| --- | --- | --- |
| 原范围内的补充和纠正 | 作为 Input 由原执行者处理，Mandate 保持不变 | 同样支持，但旧代码会把附加原话也追加到范围字段 |
| 超出原授权的要求 | 执行者交回 Router，新评估接受后建立新工单和授权 | 草案建议只要仍属同一业务目标，就可以更新原工作的范围 |
| 作者与来源可追溯 | 保留原始 Trigger、输入和路由记录 | 另有 `scope-revision` 记录，但有记录不等于范围变更规则已经合理 |

例如，原任务明确“只读调查”，后来要求“现在修复并发布 PR”，涉及新增行动授权。按原版应交回并重新接单；不能仅因为仍在解决同一个问题就默默改写原授权。已有明确的新要求可以直接作为接单依据，不必让所有者重复提出。

另一种情况是执行者自己加了原请求没有的门禁。指出这个错误是纠正执行偏差，不应为了撤销 Agent 的自设限制再建立授权手续。

**已确认：沿用原版的不可变授权与交回机制。** 原范围内补充作为 Input 处理；范围外请求交回并重新接单。旧 OSA 更新范围字段的实现不作为新版规范，本次没有修改代码。

### 重要操作与重复确认

按所有者要求，沿用 dsh 的授权与交付方式，OSA 不增加逐动作确认流程。

执行者在 Mandate 和已确定的工作、交付要求内推进。允许的动作可来自本次请求，也可来自所有者事先设置的项目交付约定，不要求每次请求都重复列出提交、推送和开 PR 等步骤。范围外的工作仍需交回，不能因工具可用就执行。

上游默认流程允许获授权的开发任务推进到实现、检查、审查和 PR 交付。合并遵循 [Delivery requirements](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/delivery.md)：未指定合并 CLI 时由人合并；指定后，默认仅在 PR 就绪、改动少于 200 行、所需批准覆盖当前提交等条件满足时启用自动合并。它没有规定所有操作都自动获准。

删除、改线上或其他发布动作是否属于本次工作，仍看实际请求和已有约定；“在测试环境部署”不能解释为“在生产部署”。不再额外套用 OSA 自创的统一审批清单。

**现状：** [Publisher](../src/publish.ts) 仍使用 OSA 既有的发布授权记录与目标校验；代码尚未因本章调整。产品上选择沿用 dsh，不表示现有发布流程已经完成适配，也不表示 Agent 能自行更改所有者的项目规则。

## 接单模式与规则

对应上游：Accept mode and rules。

| 上游模式 | 含义 | OSA 第一版 |
| --- | --- | --- |
| `off` | 不接受推断式主动工作 | 沿用这一默认行为 |
| `observe` | 记录推断请求是否值得做，不实际接单 | 当前不要求建设；有真实主动工作需求时再考虑 |
| `auto` | 按已启用规则接受推断请求 | 不默认开放 |

所有者的明确请求不依赖主动接单模式。关掉主动接单，不会阻止“修复这个问题”这样的直接要求。

已接任务按授权持续处理反馈，不属于擅自新增目标。凡是 Agent 自行发现、超出当前目标的新工作，第一版只报告建议，不替所有者接下。

上游把特定主动工作流程放在匹配规则中，把通用交付要求放在提示词中。OSA 沿用规则集中维护的原则，不在 Router 每次派发时重新生成一份门禁清单。

## 策略版本

对应上游：Policy version。

保留接单时依据的身份和规则版本。规则改变影响哪些工作，应有记录；不把新设置悄悄解释成所有者过去已经说过的话。

沿用上游的区分：准入规则决定谁可以发起什么工作，来源配置决定哪些消息会进入系统，交付要求决定结果怎样交付。修改其中一项，不自动代表另外两项一起变化。

所有者对某张任务的更正只作用于明确范围。项目级或全局规则的变更必须有相应表达，不能由 Router 从一次例外推导出来。明确取消的条件应对相关工作生效，不能被旧摘要继续引用。

关闭一个消息入口表示该入口暂停接收或发送，不自动表示业务任务被所有者叫停。消息发送失败也不能记成“已通知”。

**现状：** 当前策略版本固定为 `owner-only-v1`，任务补充另有 `scope-revision` 记录。完整的可编辑策略版本管理不属于已实现能力，本章也不要求照搬上游的全部设置面板。

## 恢复与停止

对应上游：Resume and stop。

等待答复、执行失败、执行者退出和所有者停止是不同事实。

- 等待或失败后，所有者的相关回答可以解除对应阻碍；能恢复的原工作继续，不重新询问已经给出的决定。
- 完成后的追加要求，先判断是否仍是原工作。保留已有成果，不因新会话重新执行已经完成的外部动作。
- 明确停止的任务不被普通评论、机器人反馈或服务重启自动唤醒。
- 所有者明确要求恢复已停止的工作时，这句话就是重新授权的依据。沿用上游的新接单语义并关联原工作，保留原停止记录；不再要求所有者重复说一次“确认恢复”。

任务表中的停止操作应明确对象并留记录。聊天中的停止要求也要定位对象；“停止这个部署”不能被扩大成关闭所有项目。执行者受阻不能自行记成“所有者已取消”。

这里确定授权含义，不设计另一套自动接续或停止投递机制。如何使用现有 Orca 能力结束和恢复执行，留到执行章。

### 恢复前重新核对

对应上游：Revalidation before resume。

恢复操作读取当前工单状态，判断是否已停止、原授权是否仍适用。由负责恢复的业务入口判断一次，后续内部调用复用结果，不重新解析原消息或逐层核验账号。信息充分时直接处理，不把恢复变成人工审批。

来源不可用时，保留请求并说明投递限制；身份或授权依据不再成立时，相关动作不能继续。不能把不可投递描述成“执行者马上会处理”。

上游支持多种授权依据的恢复检查；OSA 第一版只采用所有者明确请求，因此不需要照搬未启用的团队准入和机器人授权分支。

**现状：** 当前 `revalidate` 主要检查原始请求者是否仍被识别为所有者。这不等于已经实现了上述所有多项目、原窗口和有效范围核对。

## 评估没有完成时

对应上游：When Eval does not finish。

评估超时或失败表示系统还没有完成判断，不表示所有者请求不成立，更不能算任务已完成。

沿用上游的有限重试和 `unavailable` 结果：保留原始请求及原因，允许重新判断。候选尚未送到 Router 时，不应把它误算成 Router 已处理但超时。

重复提醒应合并到同一待处理事项。需要所有者介入时说明“哪条请求尚未处理、原因是什么、现在能做什么”，不要要求所有者重新输入已经保存的需求。

具体等待时间、重试次数和唤醒方式属于执行策略。本章不以增加重试层数代替解决已发生的投递或路由故障。
