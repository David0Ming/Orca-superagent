# 006 部署

本章承接 [005 面板](005-panel.md)，按上游 [006 Deployment](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/006-deployment.md) 的全部小节顺序，说明界面接入、运行环境、账号、启停与升级。

状态：2026-11-07 开发版。**一个 Orca 插件入口连接一套本机 OSA 服务和状态库，管理多个项目。** 插件与服务接口已实现；正式服务是否升级、插件是否加载和实际验收结果以本轮验证记录为准。

原版部署依赖 DeepSeek Harness；OSA 使用 Orca，因此保留部署原则与工作语义，替换宿主相关步骤。旧 OSA 脚本可以复用，但不因已经存在就视为符合新版要求。

## 运行哪些部分

对应上游：What runs。

| 部分 | 职责 | 部署关系 |
| --- | --- | --- |
| OSA 服务 | 接收请求，维护授权、工单、输入、报告和回复记录 | 多项目共用一套服务与持久状态 |
| OSA 插件面板 | 全局总览、项目任务表、任务对话及设置入口 | 接入 Orca，读取和操作同一套 OSA 记录 |
| 插件 worker | 在插件界面与本机服务之间传递请求和结果 | 使用 Orca 已有插件能力，不保存另一套业务真相 |
| Router | 跨项目定位、路由和反馈 | 一个逻辑角色，运行在明确绑定的会话中 |
| Executor 与子智能体 | 按任务执行、协作与交付 | 由 Orca 承载和调度 |
| GitHub／飞书来源 | 按需接收外部请求和回复 | 共用 OSA 服务，不按项目重复部署整个系统 |

**为什么暂选这样部署：** 需要在面板关闭时继续保存和处理工作。现有 OSA 服务已经承担这一责任，Orca 提供面板与 worker 通信，因此先验证最小连接。若原生能力已经能完整承担同一责任，就不保留多余的中间层；不因旧服务存在而默认保留它的全部机制。

本日读取的 CLI 支持 `panel`、`components`、`worker-panel` 模板，以及 `plugin.request`／`panels.handle` 通信。这证明存在接入路径，不证明 OSA 的多项目视图、后台通知和原窗口关联已经接通。具体布局能否满足使用，需要实际面板验证。

优先使用公开插件与 CLI 接口，不改 Orca 本体，不读写其私有数据库来补接口。原生能力不足时说明具体限制，再决定如何接入；不把旧可靠性方案中的宿主改造要求重新列为前置条件。

第一版随本机 Orca 使用。关闭面板不应删除任务；关闭 Orca 后不能承诺继续启动原生执行。电脑休眠或关机期间不承诺持续接单，多机接管不在本章范围内。

### 权限与隔离

对应上游：Permissions and isolation。

沿用原版的事实边界：执行者以运行环境的系统用户操作，账号配置和提示词约定不等于操作系统隔离。OSA 当前是同机、同用户的个人工具。

Orca 对运行代码的插件要求声明访问能力并取得安装批准。安装时应展示真实需要的能力；使用已获准的能力不再把每个业务步骤变成一次安装审批。插件安装批准也不等于所有业务动作都获得授权。

Router 的角色限制与具体 Agent 的工具权限分别说明。不能因加载 Router skill 就宣称它已经无法读写本机；同样不能为追求隔离重新建立已放弃的执行者凭证或围栏系统。

## 前置条件

对应上游：Prerequisites。

OSA 使用自己的实际依赖，不要求为照搬安装步骤再装一套 DSH、tmux 或 pnpm。

- 满足本项目 [package.json](../package.json) 的 Node 环境，当前要求为 Node 22.13 及以上。
- 已安装且可用的 Orca，以及与运行版本匹配的 CLI。
- 已配置所用 Agent 的账号和模型；客户端名称不能代替实际模型身份。
- 可访问的项目仓库、Git 和任务所需工具；涉及子智能体时，Orca 的实际能力与限制支持所需层次。
- 接入 GitHub 时使用可核对身份的 `gh`；接入飞书时使用相应机器人配置和 CLI。

GitHub 和飞书是可选入口，不应成为仅使用本地项目任务表的安装前提。需要发布 PR 的任务才依赖相应仓库及发布账号。

正式安装包应注明经过验证的 Orca 版本和所需接口。仅凭指南出现某个接口，不能宣称当前宿主已经通过全部接入验收。

## 账号

对应上游：Accounts。

区分“谁能提出工作”与“用哪个账号执行外部操作”。个人只有一个所有者，也可能同时使用自己的身份和 Agent 的操作身份。

### Agent 的 GitHub 账号

对应上游：Agent GitHub account。

原版面向团队，默认使用专用 Agent GitHub 账号及独立 CLI 配置。个人 OSA 不把另建账号列为默认前置条件：已有账号能满足实际请求与回复时先保留；只有需要区分发布身份或访问范围时，再配置专用账号。不会仅为与原版一致而要求所有者管理额外身份。

账号的选择需要与实际接收方式一致。原版通过 Agent 账号通知接单，旧 OSA 还有其已有仓库读取方式，不能只换登录就认为二者等价。既有输出标识用于避免把自己的回复重新当成任务；合并仍遵循已经确定的交付规则。

**现状：** 旧 OSA 使用已登录本人身份。是否改为专用账号，是根据实际使用决定的配置选择，本轮不变更账号。未接入 GitHub 的本地使用不需要处理此项。

### 飞书机器人（可选）

对应上游：Feishu bot (optional)。

沿用上游的独立机器人配置：机器人接收和发送消息，所有者账号提供请求依据。核对应用、机器人、群成员关系及实际权限，不使用错误账号代发。

接入范围按真实需要配置。不要求每个项目建一个群；群或话题怎样关联项目、任务，由已确认的领域和路由规则决定。

凭据留在已有安全配置中，不写进提示词、备忘录或安装日志。修改或删除配置前核对共享凭据的影响，避免影响所有者正在使用的其他工具。

## 安装

对应上游：Install。

安装先完成服务及必要配置，再接入插件和 Router，最后验证一条真实工作循环。首次安装与已有状态升级使用不同流程，不用初始化覆盖旧数据。

当前已有后端的开发检查命令是：

```sh
rtk proxy npm ci --legacy-peer-deps
rtk npm run typecheck
rtk npm test
```

这些命令安装依赖并检查代码。插件在 `plugin/osa`，使用 `orca plugin validate/check/test plugin/osa --json` 检查，使用 `plugin dev load` 加载；首次代码权限须由所有者批准。具体命令见根目录 README。

插件实现后，使用 Orca 原生的 manifest 校验、插件检查和安装方式。校验通过后再加载具体插件；需要的访问批准由 Orca 对该插件及其实际能力提出。开发加载与正式发行分别标明，开发目录不作为长期生产部署的隐含前提。

已有 OSA 状态优先保留。迁移先准备备份和明确目标，不能为了界面看起来干净而新开一套服务重复监听原入口。

## 机器配置

对应上游：Machine configuration。

沿用上游“固定持久状态位置，明确运行环境”的原则。

| 配置 | 含义 |
| --- | --- |
| 状态目录 | 一套 OSA 的工单、来源位置、报告、操作记录和运行日志所在位置 |
| 运行代码位置 | 当前服务使用的代码与启动脚本；升级后需要核对实际加载版本 |
| Orca 接口位置 | 与本机运行版本匹配的 CLI 和原生运行身份 |
| 项目仓库位置 | 本机可访问的仓库及已选择的执行位置，不以启动目录冒充所有项目 |
| 来源配置 | 实际接入账号、监听范围和回复位置 |
| 插件连接配置 | 连接哪一套本机 OSA 服务，不能因当前窗口变化就切换状态库 |

项目和仓库是这套服务里的数据，不为每个项目建立独立状态目录、端口或 Router 配置。

**现状：** 旧服务使用 Node、SQLite 和本机 Unix socket；启动及托管参数已有配置文件。源码修改、配置保存和进程生效分别说明，不能照搬原版的所有参数热更新承诺。

## 启动与停止

对应上游：Start and stop。

沿用原版的行为目标：拒绝重复启动，正常停止有明确结果，人工停止不被当成崩溃反复拉起。重启保留状态，先核对 Orca 原执行，不重复派工。

当前可用的查询命令：

```sh
rtk proxy node scripts/osa-service.mjs status --state /absolute/osa-state
rtk proxy node --experimental-transform-types bin/osa.ts --state /absolute/osa-state owner status
```

第一条查询服务进程，第二条读取任务等业务记录；只读查询不需要也不续租 Router 租约。面板所有者操作有明确入口，不借用 Router 接管流程。

两条查询不能互相替代：进程存活不证明 Router 已绑定、来源可用或任务正在推进。

原版脚本区分“正常运行”“运行故障”“来源等局部故障”“等待配置”，并按原因处理；这些含义应保留。旧 OSA 命令尚未提供完全相同的退出码约定，不能把原版的 0／1／2／3 直接套用在它的结果上。

| 操作 | 应有的含义 |
| --- | --- |
| 启动 | 使用指定配置和状态，确认服务实际可用；不重复建立任务 |
| 停止 OSA | 停止 OSA 处理并保留数据；说明原生执行者是否仍在运行 |
| 停止任务 | 停止明确的业务工作，遵循原生执行收尾及授权规则 |
| 重启 OSA | 恢复服务连接与记录，核对现有执行状态 |
| 关闭插件面板 | 关闭一个界面，不删除业务记录，也不等同于停止任务 |

**实现更新（2026-11-07）：** 手动 `osa-service stop` 保存停止意图，[supervisor](../scripts/osa-supervisor.mjs) 进入 `paused-owner`，不自动拉起；明确 `start` 后恢复。低磁盘等托管器内部停止不设置人工停止标记。

现有具体操作参见 [运行手册](p4/RUNBOOK.md)，其中历史账号、模型、窗口编号和并发数不是新安装的默认配置。执行维护前核对本机实际配置。

### 定时健康检查

对应上游：Hourly check。

上游把健康检查放在独立运行环境中：服务正常保持安静，来源或配置故障报告具体原因，真正的运行故障才尝试恢复，并尊重人工停止。

OSA 沿用这个责任划分，优先复用现有本机服务托管。Orca 负责执行者生命周期，OSA 的托管负责自身服务；不要再增加一套持续询问所有 Agent 的 LLM 监督循环。

恢复成功通常不需要打扰所有者。同一未解决问题合并报告；凭据、目标位置或人为停止的问题不能靠不断重启解决。原版“每小时”是其部署配置，不要求在已有本机托管之外再复制一份定时任务。

## 设置

对应上游：Settings。

按面板章的分组配置来源、准入、执行、提示词和运行环境。先检查实际身份与必要依赖，缺什么就指出什么；无关可选来源未配置，不应阻止本地任务。

个人多项目共用来源接入和准入机制，项目内保存仓库关系及已有约定。发现仓库不代表已授权执行，改变项目默认位置也不移动在途工作。

旧固定模型、强制两轮审查已移除，旧组件记录仍用于兼容工程绑定，不成为面板必填业务层级。哪些可以编辑、何时生效，按真实实现展示。

### 管理接口

对应上游：Management API。

上游面板调用本地 HTTP API。OSA 已有本机 socket 和命令入口，因此不必为模仿接口形式先重建一套 HTTP 服务。

**首选适配：** 插件面板通过 Orca 的 `plugin.request` 调用插件 worker，由 worker 对接 OSA 现有命令或本机接口。任务状态和修改继续交给 OSA 服务处理，插件不直接写另一份工单数据库。

面板操作、Router 操作和 Executor 报告保留各自角色。所有者在界面作出的决定不能冒充 Agent 报告，Router 也不能借一个通用界面接口获得所有者的全部管理权限。

服务不对外暴露通用远程命令接口。连接失败时保留未提交内容并显示真实结果，不能把插件本地状态更新当成 OSA 已接受。请求如何绑定身份、如何返回错误和刷新数据，需要通过实际插件联调确认。

## 初始检查

对应上游：Setup checks。

启动或相关配置改变时检查一次实际工具、账号与连接。正常内部调用复用已加载的配置和类型；收到失联、身份变化等实际信号后再刷新相应状态，不为每个请求重做全套检查：

- 状态目录可用，只有预期的服务实例在管理它。
- Orca 与对应 CLI 可达，所需插件、会话和调度能力实际存在。
- Router 的当前会话已绑定，后台事件可以到达，不占用人工输入框。
- 已登记仓库和执行位置可访问；必要工具按当前任务检查。
- 已启用来源的所有者身份、操作身份、监听范围及回复位置正确。
- 插件连接的是预期服务，消息和任务不会写入临时或错误的状态库。

上游会为专用 profile 配置 PATH、账号包装器和 Git 配置。Orca 还承载所有者其他窗口，OSA 不能为了适配而全局改写这些环境。需要的设置限定在 OSA 使用的工具和执行上下文，保留现有用户配置。

检查失败说明影响范围。一条飞书来源故障不应被描述为所有本地工作不可用；必要的共享服务不可用也不能掩盖成“只是界面慢”。

## 试用验证

对应上游：Try it。

原版用一个明确请求验证接单到原话题交付。OSA 的首次验证应覆盖本地主入口和跨项目隔离：

1. 在临时项目中提出一个小而明确的任务，看到它被接单、执行并返回可检查的结果。
2. 在原任务下补充范围内要求，确认同一工作收到并处理，不要求再说“继续”。
3. 在另一个临时项目提出独立任务，确认目标、目录、报告和回复不串项目。
4. 执行者需要回答时，问题到达对应任务；所有者回答后原工作继续。
5. 关闭并重新打开面板，记录仍在；受控重启 OSA 后，原生工作不重复启动。

测试 GitHub、飞书等可选入口时，再分别验证请求和结果回到正确话题。测试原窗口关联时，需要验证真实的输入和结果映射，不能仅凭窗口列表可读取就宣布接续完成。

这组验证是部署是否可用的依据。插件 manifest 校验、模拟 host 测试和后端单元测试各有作用，但不能单独替代真实 Agent 的工作循环。

## 升级

对应上游：Upgrade。

沿用原版的备份、兼容检查和状态保留原则，并按所有者偏好统一交付收敛后的集成版本。

1. 记录当前 OSA、插件、Orca 及模型配置，核对在途工作，选择合适的维护时机。
2. 生成包含已提交数据库事务的一致性备份，同时保留配置和必要交接资料。活动 SQLite 使用其备份能力，不能只复制主文件而遗漏 WAL 中的数据。
3. 检查本次数据兼容性和所需接口，保留可回退的代码与状态。旧代码不能直接读取不兼容的新格式。
4. 加载这次集成版本，核对实际运行版本、Router 绑定、来源和待处理记录。
5. 验证面板与服务重新连接，未重复派工或发送结果；配置保存不等于已有 Agent 已加载新提示词。

OSA 的单独重启不强行终止全部 Orca 执行者，具体按执行章处理。升级不会授权清理用户目录、重建所有工作树或替换原账号。

Orca 更新后核对公开插件和调度接口。出现不兼容时报告范围，先保持已有记录可查；不为追赶版本改写 Orca 应用包或恢复私有补丁路线。

### Agent 预设

对应上游：Agent presets。

原版会话依赖 `dsh-superagent-router` 与 `dsh-superagent-worker` 预设，删除预设会使原会话无法加载。OSA 不复制这些名称，而是核对所用 Agent 的模型、提示词、工具和恢复配置。

已有会话保留创建和运行时的实际配置。变更默认模型不等于已替换全部执行者；不能静默换模型、丢掉历史或为更新预设重开全部任务。

## 故障排查

对应上游：Troubleshooting。

| 现象 | 先核对什么 | 处理原则 |
| --- | --- | --- |
| 插件面板打不开 | 插件是否启用、版本是否兼容、所需访问是否获准 | 根据原生错误处理，不认为业务记录已丢失 |
| 面板显示离线 | OSA 服务及连接配置 | 保留草稿，恢复连接后读取真实状态 |
| 服务运行但 Router 不响应 | 当前绑定、待办及后台唤醒回执 | 修复对应链路，不重复创建整套任务 |
| 重启后仍是旧行为 | 实际进程、代码位置及配置 | 核实已加载版本，不以文件修改时间代替生效证据 |
| 人工停止后服务又启动 | 是否仍有托管进程恢复它 | 尊重人工停止，核对托管状态，不循环互相拉起和停止 |
| GitHub／飞书请求没有进入 | 发送者身份、监听范围、读取位置 | 保留原消息定位原因，避免让所有者反复重发 |
| Agent 完成但结果没有回来 | 业务报告、原生结算及回复渠道 | 区分尚未产生、尚未接受与发送失败 |
| 窗口空闲但容量一直占用 | 真实执行状态与资源收尾记录 | 不通过取消业务目标或强关未知窗口掩盖问题 |
| 多仓库任务被旧目标绑定拒绝 | 当前适配是否仍只支持一个目标位置 | 记录实现缺口，不把它改称多仓库需要特殊权限 |
| 一个来源报错 | 该来源的账号、范围和错误 | 优先处理局部问题，不重复重启正常工作的其他项目 |

当前首选部署形态有公开接口和既有代码作为基础，但插件到服务、任务评论到 Router、已有窗口双向接入仍需真实验证。旧版插件可行性记录只作历史证据，其中已经放弃的宿主改造和可靠性方案不作为本章依赖。
