## 需求一：同一件事可以持续接着做

对用户展示“工作线”：项目下一个有名字、可以持续推进的目标。它不是按关键词自动归类的所有同类任务，也不是一个永不退出的智能体进程。

1. 同一工作线保留目标、范围、关联项目/组件、执行位置、目录/分支、任务列表、证据和下一步。诊断、修复、审查可以是不同工单，但继承明确的归属与交接信息。
2. “接着做、又出问题、补一个要求”在指向明确时进入原工作线。跨飞书与 Router 入口使用同一记录；有多个合理归属时只问必要的选择题，不靠相同名称猜测。
3. 未完成期间允许补充需求、修 bug、等待登录/批准/外部消息。等待不等于业务取消，也不应要求执行进程一直占用席位；恢复时先核对现场变化。历史已停止的工单不能因此自动复活。
4. 默认复用适合当前工作的持久目录；只读检查和远程操作不因生成工单就额外创建本地工作树。并行写同一代码基线确有冲突时才使用隔离工作树，保留归属和回收流程；继续保留每工单独立身份和 Run。
5. 工作线、终端和目录生命周期分开：关窗口不丢工作线；工作线完成不立即删目录。清理前检查未保存产物、其他任务及已知运行服务的引用；外部引用未核实不能当作不存在。
6. 查询进展按工作线回答：已完成什么、正在做什么、卡在哪里、需要用户做什么。派工/投递/已读等状态来自回执，不能用模型的口头承诺代替。

验收：同一测试目标跨两个入口经历诊断、修复、等待人工、追加要求和执行者重启后，仍属于同一工作线，目录与交接信息可续用；独立目标可并行，冲突写入被隔离；重启后不会重复执行已完成动作。

## 需求二：备忘录属于工程，换智能体仍可用

1. 复用既有工程文档及版本化知识注册表，明确唯一可修改的事实来源；索引或自动生成的摘要不能成为另一份独立规则。先做简短备忘录，不引入新的通用记忆系统。
2. 通用偏好、Router 角色规程、项目/组件事实、工作线交接分别归属；执行者只加载当前范围。一个智能体参与多个项目时，不依赖它的个人记忆或上一段聊天。
3. 备忘录记录少而有用的事实：实际执行位置、环境与账号用途区别、容易重复踩的坑、有效解决办法及验证方式。保存来源、适用范围与核验时间；不保存密码、令牌等凭据值。
4. 已验证的普通工程事实自动维护；用户明确的业务裁决和授权范围保持原意。推测不得升级为规则，冲突不得静默覆盖，不确定时查询现场或询问用户。实时状态以工单和现场为准，不靠旧备忘录推断仍然在线或凭据仍然有效。
5. 阶段结束或执行者交接时更新当前卡点、下一步和证据位置。需长期保留的证据不只留在 `/tmp`。

验收：换一个无原聊天历史的执行者，能识别日报与客服的账号用途和运行环境差异，读到已有用户裁决与当前卡点；切换到另一项目时不带入这些项目专属规则。以上示例用于验收，不硬编码项目名称。

## 需求三：系统消息走后台，人工输入保持完整

1. OSA 派工回执、Executor 消息、看门狗告警使用与人工输入分离的后台通道；不向 Router 的 PTY 输入框写提醒文字，不自动替用户按 Enter，也不冒充人工消息。
2. 保留可靠唤醒、消息身份、确认、去重和重启续收能力。不能为了安静而让飞书目标或执行结果无人处理；投递失败应可见、可追踪。
3. 界面区分人工消息与系统事件。普通重复提醒合并；需要用户决策、人工操作或确有影响的异常才主动打扰。看门狗遵循同一规则，不能私自确认业务消息、取消工单。
4. 用户后续明确选择先实现原生聊天页，终端无干扰通道后续增强。界面形式不是需求本身。优先验证 Orca 现有结构化会话能否沿用当前 Claude Code 模型配置，实现以上行为；若需要切换入口，先展示兼容性与草稿保护验收结果，再安排迁移。不得静默更换模型或丢失当前会话。

验收：人工停在半句未发送的草稿时，连续到达派工结果、看门狗消息和飞书请求，草稿逐字不变、不被提交，后台消息仍被正确处理且来源可区分；断线重启后不丢失、不重复执行。
