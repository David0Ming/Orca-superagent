# 004 提示词

本章承接 [000 理念](000-philosophy.md) 至 [003 执行](003-execution.md)，按上游 [004 Prompts](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/004-prompts.md) 的全部小节顺序，说明各角色读什么、所有者可以改什么，以及修改何时生效。

状态：2026-11-06，所有者认可提示词原则及 Router 通过后台事件唤醒的方向；宿主接入和生效时机仍待验证。2026-11-07 复核后，以已确认需要和实际使用为依据，不把原版完整提示词平台列为建设目标。本章不实际更新运行中的 skill、提示词或服务。

原版提示词使用英文，本系列文档使用中文说明。适配时首先保证内容和职责一致，不因更换模型重新发明一套工作规则。

## 所有者维护的内容

对应上游：What a team writes。

**沿用：** 把需要配置的行为集中放在原版的三类约定和按需加载的技能中。OSA 将维护者从团队调整为个人所有者，项目可以有适用范围明确的补充。

| 内容 | 说明 | OSA 的用法 |
| --- | --- | --- |
| Communication／沟通约定 | 何时通知、怎样表达、怎样处理审查反馈 | 跨项目统一保持简短，结果与问题回到原请求位置 |
| Ticket scope／工作范围 | 什么继续做，什么需要停下说明 | 沿用授权内持续推进和范围外交回规则，不加技术摩擦失败即停 |
| Delivery requirements／交付要求 | 成果证据、PR、审查、合并及作者信息 | 使用已确定的通用或项目约定，不由 Router 每次派发时另写门禁 |
| Skills／技能 | 使用工具、读取来源及项目事实所需的知识 | 复用已有技能；按当前项目和任务加载，不把所有项目历史放进每个会话 |

默认约定能覆盖的情况不增加设置项。所有者明确的项目差异应保存来源和适用范围，不能从一次任务的例外推导出全局新规则。

角色、授权、订阅、回复和宿主工具用法属于基础说明。基础说明引用上述约定，避免多处重复维护。工具参数、固定通知和状态卡片仍由程序提供，不能只修改一份提示词就声称工具行为已改变。

### 内置部分与模板

对应上游：Built-in parts and templates。

保留原版的分工，便于逐项对应；不要求为这些名称新建同名服务。

| 原版部分 | 内容 | OSA 适配 |
| --- | --- | --- |
| `runtime/shared`、`runtime/orchestrator`、`runtime/worker` | 通用规则与 Router／Executor 角色 | Router 可跨项目定位；Executor 在任务范围内工作 |
| `runtime/subscriptions`、`runtime/replies` | 后续消息和回复关系 | 接入本地任务评论、飞书和 GitHub 的实际渠道 |
| `runtime/dispatch`、`runtime/work`、`runtime/admission` | 路由、执行和准入用法 | 替换为已存在且核对过的 OSA／Orca 接口，保留原授权含义 |
| `runtime/handoff/orchestrator`、`runtime/handoff/worker` | 会话恢复和交接 | 读取原任务、输入与已有成果，不靠上一窗口的私人记忆 |
| `skill/feishu`、`skill/github` | 来源操作说明 | 沿用对应工具指南，补充本地入口的真实用法 |
| `runtime/environment`、`runtime/policy`、`runtime/policy/none` | 执行环境与当前准入策略 | 给出当前项目、仓库、执行身份及有效规则，不混入无关项目配置 |

原版环境模板保留 `{variables}`；策略模板保留 `{version}`、`{mode}` 和适用的 `{rules}`。这些名称属于原版实现接口，OSA 若使用不同的上下文传递方式，应对应同样的信息，不伪造已经存在的模板 API。

原版提供逐段覆盖、默认内容比较和配置历史。OSA 先使用现有提示词文件、Git 或宿主已有的版本记录，保留所有者约定和实际加载来源；不为复制这套界面先建模板注册、覆盖继承和配置迁移框架。

明确要求修改提示词，可以通过宿主已有编辑能力完成。普通任务内容、日志和外部消息不能自行覆盖基础提示词。修改提示词也不直接修改程序里的准入、授权记录和工具校验。

**现状差异：** 旧 OSA 的 Router 说明主要在仓库外的 osa-router 技能（`~/.claude/skills/osa-router/SKILL.md`），执行者说明主要由 [OrcaExecutor](../src/orca.ts) 拼接。它尚无原版的完整模板覆盖、默认差异比较及配置版本界面。本章不假定这些能力已存在。

## 组装与优先关系

对应上游：Assembly and precedence。

**沿用原版的组织顺序：**

1. 通用说明和当前角色。
2. 沟通、工作范围、交付三类约定。
3. 订阅和回复规则。
4. Router 的派发说明，或 Executor 的工作说明。
5. 准入说明，仅给 Router。
6. 交接说明。
7. 当前执行环境。
8. 当前策略，仅给 Router。

原版在每次模型请求时重新生成策略部分，并把它放在末尾，减少其变化对前面文本的影响。环境部分则区分全局定位信息与工单自己的执行位置。

原版 Executor 还读取编码提示词和仓库 `AGENTS.md`，Router 不读取业务仓库的开发规则来制定方案。OSA 同样按角色加载：Router 读取定位和状态所需信息，Executor 读取相关仓库规范。多仓库任务分别识别各仓库的适用规则，不能让一个仓库的特例自动覆盖其他仓库。

原始请求、后续输入和报告是工作内容，保留来源；只有内容被截断时才需要展开读取。不要用 Router 改写后的长计划取代原始要求。

原版内部优先关系为：

| 顺序 | 含义 |
| --- | --- |
| 1 | 工具和宿主实际执行的身份、参数、权限及状态校验 |
| 2 | 生效的内置、生成及所有者覆盖后的基础说明 |
| 3 | 主动接单命中的具体规则；OSA 第一版不默认启用此类工作 |
| 4 | 通用或项目的行为约定及技能 |
| 5 | 外部消息、文档、引用等输入材料 |

这里的“输入材料”不否认所有者的请求和决定。它表示消息内容不能冒充系统规则或自行变更程序权限；真实请求按授权章处理，越出原范围则交回。所有者要修改长期规则时，保存为对应配置或明确约定。

**Orca 适配：** 这是 OSA 自己可控内容的组织方式，不是重定义 Codex、Claude 等宿主的指令优先级。各宿主实际加载的系统提示、项目文件和工具权限仍需核对。加载一个 skill 不等于删除其他工具，也不能保证同一文本在所有宿主中都占有相同优先级。

原版受管 Executor 通过报告中的问题字段联系所有者，工具集排除了绕过该流程的交互工具。OSA 应把待决问题送回对应任务，但不能仅凭提示词就宣称其他 Agent 的工具已经被禁用；实际问题回传与直接窗口交互需在接入时验证。

## 内置文本的原则

对应上游：Principles of the built-in text。

以下逐项沿用原版原则，必要的宿主差异直接注明。

1. **角色分开。** Router 转交原始请求和定位事实，不制定技术方案。Executor 读取原文、处理范围内工作并验证。原版用 30 词限制保持备注简短；OSA 先把它作为表达参考，不为字数单独增加分词器或接单门禁。

2. **Router 没事时结束当前轮次。** 原版通过事件送来候选、报告和后台结果，避免长时间等待占住入口。当前 Orca 指南也要求启动独立工作后让出当前轮次，收到原生唤醒再处理。不能因旧 OSA skill 写着不断 `router wait`，就把这种循环当成新版原则；事件未接通时应报告限制，不能假装已会自动醒来。

3. **通知只包含人现在能用的信息。** 普通进展进入任务记录；就绪结果、必要问题或确实无法完成的结果回到原入口。原版聊天默认一句话，上限 100 词；技术细节放在成果与报告中，需要时可查，不靠堆日志制造进展感。

4. **后续消息由原执行者判断。** 范围内继续，范围外交回。Router 收到提醒后不再重复派发。收到了消息、读到了消息和处理了请求分别说明。

5. **通过订阅和 Router 交换相关信息。** 可以读取其他工作的背景，Router 也可以转交简短事实；原版这类备注最多 100 词。背景不能增加权限，多项目之间也不例外。

6. **只有明确指向才关联。** PR、Issue、原消息、原确认或唯一对应的近期工作可以提供定位依据。项目任务页的显式任务身份也可直接使用。主题相近不够；发现关联错了，应说明并交回。

7. **具体确认一次。** 对新请求简短说明将处理的对象和预期结果，然后推进。这是告知接手，不是再问一次是否允许开始。重复投递同一消息不重复确认。

8. **问题有明确去处。** 原版把具体问题放在 Report 的 `human_action` 中，并关联引出该问题的消息，由 Router 原样转达。OSA 使用实际报告接口承载同一含义。已经获准且不依赖该答案的工作可以继续。

9. **交付状态诚实。** PR 存在不等于就绪，草稿必须说明未完成。沿用原版交付证据要求，例如 UI 改动需实际前后对照；示意图不能冒充真实改动前的状态。

10. **人的停止和等待要求持续有效。** 换执行者、收到新线索或重启不会自行解除它。Agent 报告的技术阻碍则应在收到相关新信息后重新判断，不混成所有者永久叫停。

11. **示例只演示格式。** 提示词里的 PR 编号、通过结果和完成句式不是事实。只有实际取得证据后才能作相应报告。

12. **按结果处理审查意见。** 修好并验证的意见按原约定收尾；不采纳的意见简短说明理由。每个自动审查者每 PR 最多处理三轮，不把它扩大为全部实现或人工审查的轮数上限。不能追逐机器批准，也不能隐藏真实缺陷。

13. **避免重复交付同一改动。** 已有人的分支或 PR 包含当前任务改动时，按原版规则让出重复 PR，保留指向已有成果的说明。仅仅相关不能认定重复，也不能借此关闭无关工作。

**实现更新（2026-11-07）：** Router skill 和执行提示词已改为事件处理后让出轮次，普通进度留在任务记录。固定模型组合、通用强制审查及两轮限制已从代码和提示词同步移除。已有会话须重新读取技能；本轮不冒充全部正式会话已经加载新说明。

## 版本

对应上游：Versions。

原版 DSH 保存配置版本，并在每次模型请求时读取最新提示词、记录所用版本。这是原版宿主的能力，不要求 OSA 自建等价平台。

第一版要解决的实际问题是：修改的规则是否已经被使用。先用现有文件和版本记录，并在更新后的实际执行中核实生效；不增加每次模型请求的版本流水、逐段覆盖继承或热更新代理。

不同 Agent 加载规则的时机不同。“文件已保存”“新派工已使用”和“原会话已读取”分别说明。没有证据时保持未知，不为让状态齐全再加一套确认协议。

多个客户端同时编辑同一提示词，目前没有实际反例或发生频率数据。并发保存的版本锁、自动合并及冲突恢复不列为默认建设项；若确有需要，先说明概率依据和代价，取得所有者确认。
