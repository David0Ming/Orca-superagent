# 003 执行

本章承接 [001 领域模型](001-domain.md) 和 [002 授权](002-authorization.md)，按上游 [003 Execution](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md) 的全部小节顺序，说明接单后的推进、交付和恢复。

状态：2026-11-06，所有者认可本章执行原则，包括重启 OSA 时先核对 Orca 原执行、避免重复派工。具体适配仍待验证。**沿用**表示保留业务规则，**Orca 适配**表示宿主不同需要映射，**现状差异**表示旧 OSA 尚未符合目标。源码、提示词或文档里已有一条规则，不是保留它的充分理由。

上游参考版本为 `8c32a9d`，本地核心仍为 `6337fc8`。Orca 部分依据本日已安装 CLI 提供的 orchestration、coordinator-loop、recovery-and-cleanup 指南；读取指南不等于完整流程实测。本章不修改 Orca 或 vendor，也不恢复已放弃的可靠性实施线。

本章引用的原版超时、轮数和退避数值用于解释机制，不要求为每个数值新增计时器或设置项。先使用已有能力解决实际停滞；改变执行策略需要具体问题依据。

## 工单阶段

对应上游：Ticket stages。

**沿用：** 工单阶段由当前等待的对象和已记录事实决定。按下表从上到下判断，先命中的条件生效。

| 条件 | 上游阶段 | 向所有者表达 |
| --- | --- | --- |
| 工单已结束 | ended | 完成、合并、关闭、无需处理或已停止，并保留原因 |
| 输入投递失败 | person / delivery | 哪条补充未送达、原因及恢复情况 |
| 有未解决的明确问题 | person / answer | 等待你的哪个决定或操作 |
| 最新报告 ready，工单尚未结束 | person / review | 成果可查看，等待相关审查或交付步骤 |
| 最新报告 blocked／failed，之后没有新的人工补充 | person / blocked、failed | 受阻或失败，说明实际阻碍 |
| 尚无派工，或派工待启动 | working / queued | 排队，说明等待条件 |
| 最新报告 waiting，或派工已结束 | idle | 等待后续输入 |
| 其余开放工单 | working | 工作正在推进；结合最新报告说明进展 |

这些是业务阶段，不是进程存活证明。没有运行中的执行者，就不能仅依据 `working` 说“Agent 还在工作”；输入入队也不证明已经送达。

上游的 `person` 分类包含投递故障。可恢复的技术故障先处理，真正需要所有者行动时再提出具体问题。普通进度留在任务记录，有可用结果、必要问题或确实无法完成时，回到原请求位置。

## 执行者

对应上游：The Executor。

**沿用：** 每张工单有负责它的执行者、持续的上下文和工作目录。执行者读取原始请求，自行调查、实现、检查并处理后续消息。Router 只做定位、路由和反馈。

上游使用每工单的 DSH Session；OSA 使用 Orca 承载的执行会话。一个执行者可以组织多个子智能体。模型和窗口形态属于执行适配，不把旧版固定的 Codex／Claude 组合当成领域规则。

**工作与审查轮次：** 上游明确没有固定的调查或实现轮数上限。文件多、测试失败或命令出错本身都不是停工理由。需要改变既有接口预期、作出新的设计决定，或可行办法反复无法推进时，说明具体影响和缺失前提。参见 [工作范围提示词](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/scope.md)。

审查按请求、项目规则和交付要求进行。上游针对每个自动审查账号设置的每 PR 三轮反馈处理上限，约束的是追逐机器审查的循环，不是正常开发的总轮数。达到上限后仍要诚实交代实质问题，不能伪造通过。参见 [沟通与审查规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/communication.md)。

**现状差异：** 旧 OSA 提示词与 ReviewGate 强制独立 Claude 审查，并在两轮后阻断。这不是 dsh 的默认规则，不直接继承为新版通用门禁。具体项目已明确要求的审查仍然有效。

### 后台工作与执行槽位

对应上游：Background work and worker slots。

**沿用：** 一轮对话结束不等于工作结束。还有必要的后台作业或子智能体运行时，保留工作状态；它们完成后，结果送回负责的执行者。交给人查看、答复或处理阻碍时，应释放活跃执行名额，保留业务报告和上下文。

| 原版 dsh 的具体方式 | Orca 适配 |
| --- | --- |
| 执行者前台 shell 超过 5 秒转后台，下一步可以接收输入 | 复用具体 Agent 和 Orca 的异步工作能力；不能把 DSH 的超时参数当成所有 Agent 已具备的能力 |
| 对话结束后后台作业最多等待 30 分钟，再终止 shell 作业并报告；子智能体可继续 | 这是 DSH 对自己作业的托管规则。OSA 不据此扫描、杀死未知进程或实现第二套看门狗 |
| 交给人时停止子智能体，供人查看的服务可保留；这类服务不占工作槽 | 用 Orca 的任务、停止和保留语义核对资源；保留窗口或演示服务不应被解释为业务还在执行 |
| Assignment 结束后收尾后台作业，再启动替代执行 | 复用原生收尾回执；仍可能运行的旧执行不能与替代执行重叠写同一位置 |

**Orca 适配：** 当前指南要求启动独立子任务后结束当前轮次，由 Orca 唤醒；收到问题、结果或异常后继续处理。不沿用旧 OSA 提示词中的常驻等待循环。终端收到带 `check` 命令的提醒时按原生命令读信，结构化聊天按实际收到的消息处理。

窗口释放与工作槽位要分别表达。`retained` 表示资源保留，不自动代表活跃，也不能自动判定已退出。状态无法确认时报告具体对象，不能强行关闭用户接管的窗口，也不能把整个项目一直说成正在执行。

**现状差异：** 旧 OSA 用 `binding.finished` 统计槽位，并要求子窗口全部 `released` 才完成部分收尾。保留窗口因此堵住槽位和后续输入的案例已经发生，见 [复核记录](stall-repair-20261104.md)。新版应恢复上游对业务进展与资源生命周期的区分；实际释放条件仍需用 Orca 回执验证。

### 准备工单目录

对应上游：Preparing a Ticket directory。

**沿用：** 工单使用明确且可持续访问的工作目录。上游在目录不存在时运行一次准备命令，限时十分钟；常见准备方式是 Git worktree，没有配置准备命令则使用空目录。准备失败保留输出，后续重试核对已有文件，不能覆盖成果。

**Orca 适配：** 通过 Orca 创建或选择工作区。已经明确关联的窗口可以使用其原目录；并行编辑相同文件会冲突时使用独立工作树。不会因为收到一条评论或更换执行者就重新建目录。

多仓库任务仍由一个负责的执行者协调，按需安排子智能体，并明确每个仓库的位置和成果。多仓库不是额外权限，也不强制拆成互不相干的业务工单。

**拟议适配：** 优先保留一个业务工单，由 Executor 组织所需的多仓执行；确有独立工作目标时才另建工单。这样能沿用 dsh 的单一负责方和反馈关系。旧 OSA 的单个 `TicketTarget` 和发布入口尚需核对是否足够，不能把当前代码限制反过来写成产品必须拆单的规则。

任务结束后保留有用产物。合并、终端释放和工作树删除分别处理；“完成后自动删掉所有目录”不是上游默认交付语义。

### 并发

对应上游：Concurrency。

**沿用：** 启动、准备目录、活跃执行和唤醒已有执行者使用工作槽位。没有名额时保留队列；某个准备步骤慢，不阻塞其他独立任务。

上游优先处理人的补充和状态请求，并为这类唤醒允许一个额外槽位，避免新任务不断占满资源后，人无法继续已有工作。CI 等自动输入使用普通槽位。

OSA 保留“人的后续要求优先续接”的原则，在所有项目间统一使用可用执行容量。项目只是工作归属，不为每个项目固定预留一套常驻 Agent。明确的资源冲突需要协调，无冲突的任务可以并行。

**第一版不新增预留槽位机制。** 已记录的卡点主要是未续接和资源收尾阻塞，额外加一个名额不能修复它们。先使用 Orca 现有容量并修正这些问题；如果实际出现正常任务长期占满容量、阻碍人工补充，再说明频率和影响，经所有者确认后决定是否采用额外名额。原版有此功能，不代表 OSA 现在需要实现它。

### 执行环境变量

对应上游：Execution variables。

**沿用：** 执行者和目录准备步骤读取一致、明确的环境信息，不靠猜测当前窗口或默认目录。

| 信息 | OSA 应给出的内容 |
| --- | --- |
| 工作身份 | 工单、当前派工、原始请求及实际 Orca 执行身份 |
| 位置 | 项目、相关仓库、目录和分支；多仓库分别列明 |
| 来源 | 发起请求的消息、话题及实际回复位置 |
| 交付配置 | 适用的账号用途、仓库规则和已配置工具 |
| 交接 | 已有成果、待处理输入、问题和证据位置 |

上游使用 `DSH_SUPERAGENT_*` 变量；OSA 不要求保留相同变量名，复用已有工单读取、交接和 Orca 上下文即可。一般环境说明不包含凭据值；来源内容不能直接改写服务配置或准备命令。

这些信息帮助正确执行，不构成操作系统安全隔离。个人同用户环境的边界仍按第一章说明。

## 合并

对应上游：Merging。

**沿用：** 是否自动合并由已确定的交付要求决定，Router 不自行合并或批准。可用 PR 就绪后应先交付给人，不必等合并才回复。

上游默认要求使用交付配置指定的另一个账号的合并 CLI；未指定时由人合并。启用自动合并还需满足：本工单打开的 PR 已就绪、增删总计少于 200 行、所需批准覆盖当前提交；涉及可见行为时，交付要求还应指定相应批准。推送新版本前撤回旧的自动合并。

这些是 [上游交付规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/prompts/team/delivery.md)，不是 GitHub 一律禁止作者合并，也不是 OSA 要新增的一套审批服务。更严格的项目规则仍适用。

多仓库工作按各仓库规则合并，并记录整体是否可用。不能把其中一个 PR 合并解释为全部完成，也不承诺跨仓库合并具有原子性。需要兼容的接口、版本或发布顺序由 Executor 按实际目标协调。

## 工单怎样结束

对应上游：How a Ticket ends。

**沿用：** 没有需要跟踪的 PR 时，符合要求的 `ready` 报告可结束工单；无需继续处理时用 `dropped`，如实说明原因。原始要求、证据、订阅和后续关联仍保留。

`ready` 是所要求的成果已验证、可供使用或审阅，不表示“刚创建了 PR”。未完成的草稿按实际限制记录，不能为了结束流程写成成功。

**Orca 适配：** OSA 业务报告与原生 `worker_done` 分别表达业务结果和执行尝试的结算。服务应接收并保存报告，再确认相应消息；原生成功结束不能替代成果证据，原生失败也不能被报告成成功。

### Pull request

对应上游：Pull requests。

**沿用：** 工单跟踪其发起或承接的 PR。自己创建的 PR 均不再开放时，或没有自己创建的 PR 而所跟踪的 PR 全部关闭时，按相应结果结束；保留合并与未合并关闭的区别。

如果还有恢复、重试或已经接手的后续工作未完成，PR 关闭不立即结束整个工单。后续报告与 PR 状态共同决定结果，不以单一事件覆盖未完成工作。

上游用仓库和分支末段与工单短名关联 PR。OSA 可复用已核实的关联方式，但多仓库时必须带仓库身份，不能靠同名分支猜测。自动发现或执行者登记后，都要保持原始请求与结果的联系。

聊天来源在需要时收到一次最终结果，GitHub 本身已有的合并通知不重复发送。多仓库任务还需核对共同目标是否满足，不把“所有 PR 已关闭”包装成“业务已成功”。

### 后续输入与背景话题

对应上游：Follow-ups and context Threads。

**沿用：** 工单话题上的人工补充由当前执行者判断：范围内处理，范围外交回。Router 不再重复派发一遍。背景订阅提供信息，不扩展授权，也不自动恢复已结束工作。

上游根据消息实际进入 Session 的历史及后续报告或轮次结束判断已读；未被接手的后续请求在工单结束后释放回评估。OSA 应实现相同含义，但不能把 Orca 的送达回执直接当成已读或已处理。

**Orca 适配：** 当前指南说明，向本地已结算或关闭的 worker 发送后续消息，可以形成原生 follow-up Task，并返回实际处理方式；配对服务器有不同限制。应优先验证并使用这一原生能力，不照搬旧 OSA 对“必须先把所有窗口清完才能送下一条”的假设。原生 Task 变化不自动创建新的业务目标或授权。

上游在活跃订阅期间轮询话题，结束后还保留一段轮询时间，默认两周；此后通过普通来源入口接收消息。这不是两周后删除历史。OSA 的本地任务记录和已关联成果也应保留，具体来源轮询按接入能力处理。

## 故障与恢复

对应上游：Failure and recovery。

### 执行者受阻或失败

对应上游：Executor blocked or failed。

**沿用：** 能自行解决的技术摩擦继续处理。真正无法推进并需要人的决定、资源或操作时，报告具体原因和剩余工作；不因普通审查意见或一次命令失败就要求人重新派工。

上游先对短暂模型或网络错误做三次退避重试。确认为失败或受阻后，自动 CI／机器人输入只记录，不继续唤醒工作；人的相关输入、后续有效报告或显式重试可以解除对应等待。准备目录失败不按模型网络错误盲目重试。

受阻不封死会话。人的新线索、纠正或回答到来后，执行者重新判断；如果原范围内已经可以推进，就继续。明确由人叫停或要求等待确认的工作仍保持停止。

**Orca 适配：** 复用原生失败、停止、重试和回执查询。Orca 的启动失败熔断与 dsh 的模型请求重试不是同一计数，不能叠加一套无限重试，或换 Run／Task 绕过原生限制。做不到自动恢复时，报告准确状态。

### 重试

对应上游：Retry。

**沿用：** 重试用于已有工作投递失败、受阻或失败后的恢复。它保留业务工单、已有成果、输入及授权，不把同一个问题重新解释成独立需求。

上游为重试创建新的 Assignment，复用同一 Executor Session、目录、分支和 PR。已有会话保留原模型；新会话才使用创建时的模型选择。

**Orca 适配：** 原生失败尝试通过同一 Task 的 `--retry-of` 关系恢复，不能拿新的 `--spec` 冒充原任务重试。OSA 的 Assignment 与原生 Dispatch 如何关联，应保留每次尝试的真实记录，而不是强求它们是同一个概念。

重试由执行适配读取本次恢复所需的原生结果，使用已有回执和明确目标，不让入口、业务函数和辅助函数反复检查同一身份、Git 状态或全量子任务。超时、沉默和 `unverifiable` 不证明进程已退出；无法确定时报告受影响任务，不盲目重复外部动作。

**现状差异：** 旧 OSA 另设两次 recovery 上限和子资源限制。新章不把这些数值直接视为业务规则；恢复要服从原生能力和真实状态。若无法原生续用同一会话，应使用已授权的新执行及持久交接，并如实说明未保留模型会话历史。

### 重启

对应上游：Restart。

**沿用结果要求：** 重启后保留工单、目录、订阅、待处理输入和报告。执行者根据交接和已有回执确认本次下一步；仅对结果不明且影响下一步的动作补查现场，不在每次恢复时重做全量仓库、窗口和外部状态检查。

原版 dsh 的宿主重启会结束在忙的 Assignment，并创建带恢复说明的新派工；已在等待、就绪、受阻或失败的工作通常保持原状，有后续输入时再按规则处理。它还保存哪些输入已进入 Session，以补回未读内容。

**Orca 适配：** 重启 OSA 不等于重启 Orca，更不意味着所有 Agent 都已退出。先恢复记录并核对原生身份；仍在运行的执行者继续关联，不能仅因 OSA 重启就复制一批执行者。

原生不能确认的执行或输入状态明确报告。这里不恢复此前放弃的自动接续、代际围栏或原生输入流留存方案，也不承诺 DSH 宿主专有的会话恢复能力在 Orca 中天然存在。

### 持久保存的工作

对应上游：Stored work。

**沿用：** 路由结果、待派工、待投递、待回报等先存下来，再执行。失败保留原请求和原因，恢复时继续同一条工作，不能悄悄丢弃或凭空宣称完成。

上游对内部转交和投递使用从 2 秒增加到最多 1 分钟的退避；连续失败后显示系统问题。Router 的报告转交和通知各自保序。

OSA 复用现有持久记录和 Orca 操作回执。明确未发送的临时失败可以重试；外部动作结果未知时，先查询实际结果。SQLite 里写入成功、Orca 已接收、执行者已处理分别记录。

报告在 OSA 暂时不可用时可通过原生信箱保留，服务保存业务回执后再确认。这是现有适配路径，仍需按具体场景验证，不把一次联调当作任何中断情况都不会出错的证明。

### 来源失败

对应上游：Source failure。

**沿用：** 分别记录消息来源和具体话题的读取错误。一个仓库或话题失败，不让其他项目全部停下；读取位置只在对应事件保存后推进。

原版 GitHub 来源会重试 404，因为私有仓库访问丢失也可能返回 404；确认删除或持续失败到既定期限后，保留原因并结束该项重试。原版默认持续失败期限为一天，错误项不会被报告成成功读取。

飞书事件消费失败、话题轮询失败和格式错误分别记录。单条坏数据不应使整批消息消失。OSA 沿用这些错误含义，具体原生响应和接入方式以实际来源为准。

### 回复渠道失败

对应上游：Channel failure。

**沿用：** 对外消息先保存，再发送；失败退避重试。上游从 5 秒退避到最多 300 秒，同一任务到同一对话保持必要顺序，无关任务不跟着阻塞。

入口暂时关闭时等待；目标确实不再接收或不在监听范围时，记录丢弃原因。找不到原审查评论时，上游可以回到相应 PR 的讨论位置；不能猜测另一个无关收件人。

OSA 的任务评论、飞书回复和 GitHub 回复遵守同样的语义。结果应回到原请求位置，发送失败必须可见；不要求所有者自己去多个窗口寻找已经产生的成果。

### 暂停处理

对应上游：Pause processing。

**沿用：** 上游的暂停处理停止新评估、新派工、输入投递和回复；来源继续保存事件，已经运行的一轮工作不被强行中断。暂停期间评估期限顺延，恢复后处理保存的工作。

这是服务处理的暂停，与明确停止一张业务工单不同。暂停不撤销授权，也不抹掉未处理消息；恢复时仍核对该工作是否已被所有者停止。

**现状差异：** OSA 当前有项目暂停等操作，但不能把它们当成已经完整实现了上游全局暂停。界面和程序需表达实际范围，不用“暂停”一词暗示所有进程都已停止。

### 配置无效

对应上游：Invalid configuration。

**沿用：** 来源配置无效时，停止使用这份配置并报告具体原因。不能改用另一个账号、仓库或项目来掩盖失败。

如果仅一个来源有问题，隔离该来源；如果共享服务无法启动，明确说明受影响范围。保留已有任务和待处理记录，修复后按原身份恢复。
