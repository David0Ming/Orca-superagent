# OSA 会话面板

读取 Orca 原生 Run、任务、Dispatch、消息和执行记录。侧栏使用 Orca components API；Run 是 Router 收件箱，task 是工单，ctx/Dispatch 是一次执行尝试。调度仍由 Orca 原生编排负责。

- 范围：当前工作区、项目、全部 OSA Run。无法从当前窗口识别工作区时可手动选择。
- 搜索已载入 Run 的任务原文、结果及最近消息；列表仅返回摘要，展开标题默认只读最近一轮（最后用户输入及后续智能体文字回复，不含工具批量输出），缺少用户输入时标明不完整；执行者最近一轮、执行历史、Router/Executor 往来消息分别提供查看/收起；历史与最近一轮互斥，往来消息按需展开，收起任务标题会重置内部展开状态。默认读取最近 20 个 Run，可加载更早的 Run。
- 筛选：智能体、状态；分组：Run、项目、工作区、智能体；排序：最后更新、标题。
- 分区：阻塞（每张 blocked 工单，以及活跃 Run 的 failed 工单；每个 Run 的未回复 question/escalation（含已读）聚合为一条“有消息待回”）；待开始（pending/ready）；进行中（dispatched 或关联执行者在线，failed/blocked 和待开始优先）。completed/succeeded/success/done 始终隐藏，即使窗口在线。行首不显示状态图标；副标题前仅显示已知 Claude/Codex 原生图片，状态文字与轻色调细边框表达状态。
- 无在线执行者、无 pending/ready/dispatched 任务的 Run 收入底部“历史”，默认折叠，保留死亡 Run 摘要或历史工单；failed/blocked 本身不使 Run 活跃，但 blocked 始终单独留在“阻塞”，其余非活动工单进入历史，不重复归类；空分区不显示标题。副标题展示状态依据或最新问题主题及相对时间。
- 行内 `@` 单击等待 300ms 后把任务、Run、执行窗口和工作区定位填入 Router 输入框，绝不按 Enter；双击只定位窗口，取消待执行的单击；没有终端绑定时需选择 Router 窗口。原生聊天 Router 暂不支持。点击标题展开只读会话与往来记录，再次点击收起；面板不提供直接回复，沟通统一通过 Router。重新判断只把“条件可能具备，请重新判断”及 Run/任务/派发标识发送到该 Run 当前真实绑定的 Router 收件箱，不直接驱动执行者、不启动会话。failed 的“交给 Router 重新判断”直接显示在行内，其余位于展开详情；没有真实 Router 绑定时，failed 行按钮禁用，发送前重新核验真实绑定，不使用旧环境文件的 HANDLE。
- 没有停止、删除、释放执行者或修改 Run/任务的接口。
- 刷新每 15 秒进行，隐藏时暂停；切回面板先显示 Orca 按工作区保留的上次完整快照并后台更新；读取复用最近 15 秒的同查询、同窗口快照，定时与手动刷新强制读取最新数据；一次替换完整列表快照，失败保留上次数据。展开详情单独读取。

读取限制：最近消息窗口为 1000 条；默认最多读取 32 条、显示至多 12000 字；Orca 首次读取返回尾部窗口，cursor 用于继续读取新增输出，并不表示当前窗口是旧页；尾部 32 条内缺少用户输入时只展示最近回复并明确提示本轮不完整。显式执行历史读取最近 50 条原始记录，遵守 Orca 的截断结果。详情显示来源及截断提示，可继续读取后续新增记录。搜索覆盖已载入的 Run，不代表搜索未加载的历史或全量 transcript。

```sh
orca plugin test plugin/osa-panel --json
orca plugin check plugin/osa-panel --json
orca plugin shot local.osa-tasks --width 335 --out /tmp/osa-panel.png --json
```

测试使用模拟 CLI 验证定位和 Router 重新判断，不向真实执行者发送内容。运行时需要已有的 trusted-worker 权限及 workspace:read，只读当前工作区名称、分支和终端列表。列表与组件尺寸受 Orca components API 控制，不保证与内置会话历史像素级一致。

纸笔侧栏图标是所有者授权的唯一 Orca 本体例外：`tools/paper-pen-patch.py` 对当前安装版本的两个 renderer 文件做定点替换并保留备份，可恢复。Orca 更新后需重新核对；当前窗口重载后生效，工具不自动重载。智能体图标取自 Orca 原生 Claude/Codex 资源，PNG 保留透明背景。

待回复计数与“有消息待回”共用同一规则：仅发给 Run/Router 的 question/escalation，并排除 msg_stop_ 及已知系统投递/停止/等待提示回执。Orca 的 status 无可靠人工作者标记，故不凭正文猜测为人工决策请求；任何消息（含未读/未回复）均不维持 Run 活跃。任务自身的 failed/blocked 状态及原始历史依据仍保留。

工单消息按明确 taskId、dispatchId 归属；仅没有这两种标识的旧消息才按关联终端兜底，同一终端的其他工单消息不会混入。

消息区分已送达、已读和已回复：读取或 check 的 handled 不等于解决。仅原生 status 回复的 thread_id 精确指向问题、收发反向、主题符合 Re: 原主题且时间不早于问题时，确认已回复；任意同线程状态不算。嵌套问题沿用根 thread 时无法证明回复指向，保守保留待处理；最近 1000 条窗口之外也不能推断已答。面板提醒使用 payload.source=osa-panel，自发给同 Run 的提醒及 queue-scan status 不维持待处理状态。点击重新判断本身不会移除工单，直到 Orca 真实状态或待回复证据发生变化。

“最后更新”优先使用 task.updated_at；缺少时取实际完成、关联消息、当前派发时间的最新值，不以创建时间充当更新。派发时间按 ctx 缓存、分批读取，失败显示警告且不编造时间。已读未答仅在活跃 Run 进入阻塞区，死 Run 的旧问题归历史；真正未读的新问题可单独提示，但不复活 Run。活跃 Run 的完成工单仍隐藏，仅分组头显示“已完成 N”：按 Run 或真实工作区/项目/智能体归属计数，相同分组跨分区只显示一次，不把没有归属的工单猜到其他工作区。
